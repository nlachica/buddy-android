F1 [major] Foreground promotion can crash instead of refusing the reading - `wear/src/main/java/app/buddy/assistant/wear/ReadAloud.java:77`: only `startForegroundService()` is protected by the catch at lines 64-69. The later `startForeground()` runs in a separate callback and is unguarded. Android can reject promotion with `ForegroundServiceStartNotAllowedException`; its [foreground-service launch guidance](https://developer.android.com/develop/background-work/services/fgs/launch) explicitly catches that exception around promotion itself. If permission to start from the background is lost before promotion, this callback crashes the watch process before sending NOT_PLAYED. The phone then sees a disconnect/unknown outcome and deliberately does not replay, so the reply is lost on both devices. This is distinct from the accepted risk that background playback may be unavailable: that risk promises a safe phone fallback. -> Handle promotion refusal in `onStartCommand`, close the current reading with NOT_PLAYED and stop/release the service before returning. Exercise a successful service-start request followed by rejected promotion; require one refusal and no player start.

F2 [major] Pending service starts can open the current channel twice - `wear/src/main/java/app/buddy/assistant/wear/ReadAloud.java:84`: every start command reads the mutable static `channel`, creates a new Speaker, overwrites `speaker` at line 102 and calls `getInputStream`, without checking whether that channel already has a player. Concrete ordering: channel A is accepted and requests a service start; the phone cancels A and opens B (for example, stop followed by another Setup sample); B replaces A and requests another start before A's start command is delivered. Both commands now start B. If the first input callback already played, its Speaker is orphaned and cannot be silenced through the static field; otherwise two input requests are still issued for B. Google's [ChannelClient contract](https://developers.google.com/android/reference/com/google/android/gms/wearable/ChannelClient) permits `getInputStream` only once per channel. A failed second request can report NOT_PLAYED while the first player has already sounded, causing phone replay or truncation. Main-thread serialization does not associate these delayed start commands with their originating channel. -> Make player startup idempotent for the current channel, using the existing non-null `speaker` as the pending/playing guard (or carry and validate a channel token). Do not replace an existing player merely because another start command arrived. Add a controlled ordering check with A and B accepted before both start commands, and a check that hush still reaches the only player.

F3 [minor] A late input stream is discarded without being closed - `wear/src/main/java/app/buddy/assistant/wear/ReadAloud.java:106`: after hush or replacement while `getInputStream` is pending, the success callback calls `sp.stop("replaced")` but never passes it `in`. `Speaker.stop()` can close only its own `in`, assigned by `Speaker.play()` (`wear/src/main/java/app/buddy/assistant/wear/Speaker.java:48`). In this ordering that field is still null, so the newly delivered stream leaks. The [ChannelClient documentation](https://developers.google.com/android/reference/com/google/android/gms/wearable/ChannelClient) requires returned streams to be closed when no longer needed; closing the channel is not a substitute. -> Explicitly close the delivered `in` in the stale callback, handling IOException. Check cancellation before stream delivery with a close-counting stream.
