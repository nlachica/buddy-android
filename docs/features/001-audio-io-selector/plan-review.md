# Plan review: 001-audio-io-selector

## Round 1 - Plan Reviewer (gpt-6-astra)

F1 [major] Reconnect only works at the next start or user tap - DW4 requires the saved device to be used again on reconnect (`brief.md:28`), but `use()` checks availability only when called, returns immediately when the device is missing, and the release poll checks voice activity rather than device changes (`plan.md:57-74`). No hook observes connection changes. Start live voice with the saved watch absent, then connect it after `connected()`: nothing reapplies the saved choice. Disconnect/reconnect during an existing call has the same gap; the bar also refreshes only on begin/tap (`plan.md:103-106`). Android explicitly ends a communication-device selection on disconnection ([AudioManager API](https://developer.android.com/reference/android/media/AudioManager#setCommunicationDevice(android.media.AudioDeviceInfo))). -> Add a small device-change callback, or extend active-session polling, to reconcile the saved preference, release the override on loss, reapply on reconnect, and refresh visible device state. Keep watching an active session even when its saved device is initially absent. Extend D1 to unplug/reconnect during the same live session without tapping or starting another utterance, and check Settings while it remains open.

F2 [major] Switching live voice to Auto can pause the agent and end the call - The proposed exemption is only `MODE_IN_COMMUNICATION && AudioRoute.on()` (`plan.md:86-89`), while selecting Auto or falling back for a missing device clears `on` (`plan.md:59-71`). Chromium still holds communication mode during live voice. Thus, with an operating agent and a selected route, switching the chip to Auto turns Buddy's own ongoing call into a newly detected external call: `AutoPause.java:147-151` invokes auto-pause and `BuddyService.java:635-637` ends live voice. This violates DW5 (`brief.md:29-30`); E3 only checks card speech with a device chosen (`plan.md:167`). -> Track/exempt Buddy's live communication activity independently of whether a route override is selected, including its teardown interval, while retaining real-call modes and external call notifications as pause signals. Test live voice with an operating agent under Auto, selected-device → Auto mid-call, missing-device fallback, and a real incoming call.

F3 [major] The other-call guard is bypassed for every live start - `use()` skips routing for an existing call only when `!CodexLive.on()` (`plan.md:61-62`), but its start hook runs after `ses = s` (`plan.md:82`; `CodexLive.java:192`), and `CodexLive.on()` is exactly `ses != null` (`CodexLive.java:113-115`). Consequently an existing phone/VoIP call is never protected by this guard when live voice starts; the later connected hook also bypasses it. Neither `ChatActivity.java:1769-1775` nor `CodexLive.java:183-199` checks for another call first. This introduces the forced device selection the guard claims to prevent; Android gives routing priority to the app controlling audio mode ([AudioManager API](https://developer.android.com/reference/android/media/AudioManager#setCommunicationDevice(android.media.AudioDeviceInfo))). -> Detect a pre-existing external call before publishing the Buddy live session/opening the WebView, and carry that result through routing decisions, or reject live start while that call is active. Also do not let an existing route flag bypass protection for MODE_RINGTONE/MODE_IN_CALL. Extend E4 to live start and a quick-switch attempt during an external call, not just read aloud.

F4 [minor] Specify cleanup after selecting Auto during live voice - The plan relies on delayed cleanup to undo Chromium's hang-up restoration (`plan.md:188-190`), but switching to Auto calls `release()` immediately and clears both ownership flags (`plan.md:59-71`), without saying whether a final cleanup remains scheduled. This matters after starting live on Speaker: Chromium saves speakerphone state when entering communication mode and restores it on exit ([AudioManagerAndroid.java, setCommunicationAudioModeOn](https://chromium.googlesource.com/chromium/src/+/main/media/base/android/java/src/org/chromium/media/AudioManagerAndroid.java#267)); its Android 12+ selector can implement that restoration by selecting Speaker again ([CommunicationDeviceSelectorPostS.java](https://chromium.googlesource.com/chromium/src/+/main/media/base/android/java/src/org/chromium/media/CommunicationDeviceSelectorPostS.java#130)). -> State explicitly that clearing the user's override mid-call retains any required post-WebView cleanup responsibility. Add Speaker → live → Auto → hang up to E1 and verify both normal mode and no remaining Buddy communication-device request. This is a lifecycle clarification; it does not require replacing polling with per-engine end hooks.

F5 [minor] Permission verification is recorded as completed without evidence - `plan.md:113-117` and `decisions.md:33-38` say the no-BLUETOOTH_CONNECT path was "Checked on device (test A3)". The recorded device evidence is only system `dumpsys` output and says the watch *should* appear (`research.md:62-67`); `verify.md` contains no results, and A3 is still a future APK check. System-shell visibility does not demonstrate app-level enumeration or successful routing without the permission. -> Mark this as awaiting A3 and retain the proposed no-new-permission approach pending the actual app test; append a correction to the decision rather than treating the test as already passed.

VERDICT: REVISE

### Planner response (round 1)
F1: accepted - The release poll now reconciles. Every `use()` starts a voice session (also under Auto) that lasts until about 1.5 s after Buddy's voice stops. On each 300 ms tick while the voice is active, `reconcile()` looks up the chosen device. If it's lost, Buddy drops to Auto behavior (`drop()`). When it's back, Buddy applies it again, with no tap or new utterance. A call or dictation that starts while the device is away keeps being watched. `AudioRoute` gets no new listener. The voice-bar chip re-reads its label about once a second from the bar's existing ticker. Settings re-renders from an `AudioDeviceCallback` registered while the screen is resumed, the same pattern as its other listeners. D1 now covers Settings left open, the watch going off and on during one live call, and a call started with the watch away.
F2: accepted - The AutoPause exemption is now keyed on Buddy's own communication mode, not on the route flag. `MODE_IN_COMMUNICATION` isn't a call while `CodexLive.on()` is true, plus a 3 s tail that `callNow` tracks to cover the page's teardown after End. It also isn't a call while `AudioRoute.ownsMode()`: Buddy set the mode itself for read aloud or dictation through a chosen device, and that flag is cleared in the same main-thread step that resets the mode. So live voice is exempt under Auto, after a switch to Auto, and while the device is away. Ringing, phone calls and call notifications still pause. E3 now covers those cases, End during a task, and a real call.
F3: accepted - "Another call" is decided once per voice session, from the mode read when the session starts, and kept for the whole session. `CodexLive.start` calls `use()` before `ses = s` and `openPage()`, so it reads the mode from before the live call. The posted part still runs with `CodexLive.on()` true, so Buddy leaves the mode to the WebView. Ringing or a phone call mid-session (any mode other than normal or communication) also stops routing, whatever was applied. Rejecting live start during a call was not taken: that is new behavior beyond the brief. E4 now covers live start and a chip tap during a call, and a call ringing while Buddy reads aloud through the watch.
F4: accepted - `drop()` (on a switch to Auto, or when the device is lost) clears the device at once but leaves the session's `dirty` mark. `finish()` clears the communication device again, and resets any mode Buddy set, after the WebView's teardown. That undoes a speaker restored by Chromium at hang-up. The plan now states that this relies on Buddy and Chromium sharing the application-context `AudioManager` (one audio-service client), and Risks has a fallback if they don't. E1 adds Speaker → live → Auto → End.
F5: accepted - The Permissions section and the decision now say the no-permission path is waiting on A3, since the research only has the system's `dumpsys` output. A3 checks that Buddy can list and select the watch and play on it with no Bluetooth permission. A correction is appended to `decisions.md`, and the earlier entry is left as written (append-only).
