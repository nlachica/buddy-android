## Research 2026-11-15 (Researcher, Sonnet 5.5)

## Summary
- `linux/buddy-run` has **no trap at all** (`grep trap linux/buddy-run` finds nothing) and sends `buddy_done` only on its last line (`linux/buddy-run:998`), after `wait $!` (`:996`). If the outer wrapper dies (TERM/INT/HUP/kill -9) there is no `buddy_done`, and the run subshell (`:921`-`:994`) is orphaned and keeps running.
- Structure: outer script starts a subshell `( ... ) &` (`:921`/`:994`), writes its pid to `$S/pid` (`:995`), `wait`s, `rm -f pid`, then `event buddy_done`. Inside, per backend: `run_<agent> | stream_<agent>`, then `status=${PIPESTATUS[0]}` (e.g. claude `:980-981`).
- `buddy_error` for a dead agent is sent only if the status is non-zero, not 143, **and** `$S/last-error.log` is non-empty (`:989`). A `kill -9` of the agent with empty stderr gives `buddy_done` but **no** `buddy_error` (reproduced, below). Clean exit 0 with no `result` event also gives no error.
- The stream loop (`stream_claude` `:398-405`, `while read`) ends only at EOF of the pipe. If the agent dies but a descendant (MCP stdio server, `sleep &`, a daemon) inherited its stdout, the pipe never reaches EOF: the wrapper blocks forever, no error, no done (reproduced). This is the most plausible root cause of the hour-long hang. The "state R + zombie `run_claude` child" was **not** reproduced (unverified why it spins; the zombie fits a subshell never reaped because its parent sat in the read loop).
- App side: a run ends only on `buddy_done` (`ChatHub.java:703`) or the give-up timer (`ChatHub.java:326-335`). That timer is **one-shot**, armed at send (`:336` `postDelayed(..., giveUp)`), and fires only if `lastEventAt` is >= giveUp old at that exact moment. Any event or any phone-tool call in the first 180 s (`onEvent` `:557`, `onToolActivity` `:550` which touches every running chat) defeats it, and it is never re-armed. So a run that produced events and then died is never ended by the app.
- The app has no pid knowledge: the only pid is the shell's `$S/pid` (`~/.buddy/sessions/<id>/pid`, pid of the run subshell, `buddy-run:995`), readable from the app via `Linux.root(app)/root/.buddy/sessions/<id>/...` (precedent: `ChatHub.lastError` reads `last-error.log` that way, `ChatHub.java:~345`). `Helper.run` starts `buddy-run` as an app-side `Process` and `waitFor()`s it (`Helper.java:60-70`) but does not tie its exit to a session.
- Sub-agents are ordinary chats with `parent` set (`Helpers.java:20`, `:90`). The parent's "Waiting for the sub-agents" is the status of its in-flight `subagents`/`delegate` MCP tool call (`ChatHub.java:1109`, `strings.xml:2025`). `Helpers.await` (`:156-181`) loops while any helper `running` for up to `WAIT_MS` = 8 min, then reports "still working". A helper ends only via the same `buddy_done`/give-up paths, so a stuck helper keeps `running` true forever; `await` also returns when the parent is not running (`:161`, stops helpers). So "release the parent's wait" = ensure every helper's `running` clears, and a parent clear releases helpers.
- No hard ceiling per sub-agent exists (grep: only `GIVE_UP_MS` 180 s / `LOCAL_GIVE_UP_MS` 15 min via the one-shot above; `WAIT_MS` bounds one wait call, not the run).
- Tests: `linux/test/run.sh` only feeds recorded agent stdout through `stream_<agent>` via `BUDDY_TEST_STREAM` (`buddy-run:914-918`), with `post` replaced by `cat`. It never exercises the run/wait/done flow, so a regression test for the dead-agent case needs a new harness (fake agent on PATH + capturing `post`). CI runs it as job `helper-tests` (`.github/workflows/build.yml:14-20`). No Java unit tests exist (`app/src/test` absent).

## Reproduction (sandbox; no real chat touched)
Setup in `/tmp/rh`: copy of `buddy-run` with `URL` sed-changed to `127.0.0.1:18765`, a python listener there that logs POST bodies, `HOME=/tmp/rh/home`, fake `claude` in `$HOME/.local/bin` (first on buddy-run's PATH). Run: `bash buddy-run tok ask <sid> claude 0 hi`. Fake `claude` prints `{"type":"system","session_id":"abc"}` then:
1. **Exits with status 3, empty stderr**: events = the system line, `buddy_done`. **No `buddy_error`** (`:989` needs non-empty last-error.log). App would show a finished run with no explanation.
2. **`kill -9` of the agent** (after 1 s): bash prints "Killed", events = system line, `buddy_done`. **No `buddy_error`**, same reason.
3. **Agent dies but leaves a child holding its stdout** (`(sleep 30 &); kill -9 $$`): 4 s later the wrapper (3 bash procs) is still alive in S, events = only the system line: **no error, no done** until the orphan exits. With a long-lived orphan this is an indefinite hang. (Stdin/stdout inheritance matches real agents: MCP stdio servers, Bash-tool background jobs, Codex sandbox helpers.)
4. **TERM to the outer wrapper** while (3) is stuck: the outer dies, the subshell (`$S/pid`) and stream loop survive re-parented to pid 1 (ppid 1), **no `buddy_done`**, `pid` file left behind. This is "killing the wrappers by hand did not help" (the app was never told).
Not reproduced: bash spinning in state R with a zombie child (hour-long). (unverified cause.) Beware when experimenting: `pkill -f` patterns also match your own shell and the live Buddy `buddy-run` processes on this phone; kill by pid.
Cleanup done: listener and orphans killed.

## Prior art
- Only repo-local code was inspected; no upstream issue/library search done (not needed to map the fix). Bash facts used: a pipeline's reader gets EOF only when all writers close the pipe; `trap ... EXIT` runs on TERM/INT/HUP exit but not on SIGKILL of the wrapper itself (standard bash semantics; the reproduction in item 4 shows the current lack of a trap).

## Constraints and risks
- SIGKILL of the wrapper can never run a trap: app-side detection is still required (brief item 3). Also proot environment: `Linux.builder` runs buddy-run under proot; `pgrep`, `/proc/<pid>` and `kill -0` are used by existing code (`:39-60`, `:269`) so they work there.
- Orphaned agent descendants hold the pipe: a fix must not rely on EOF alone. Options for the Planner (not decided here): wait on the agent pid instead of the pipe; run agent via a process group and kill the group when the agent leader exits; watch from the subshell. `kill_tree` uses `pgrep -P` (children only, orphans re-parented to 1 are missed).
- The retry blocks re-run `run_x | stream_x`; one run section can invoke the agent up to 3 times (agy). A trap/idle watcher must stay valid across them.
- `stop` path: `kill_tree` of `$S/pid` then removes pid and posts `buddy_stopped`; `buddy_done` comes from the outer wrapper. `buddy_done` is ignored by the app when `!ses.running` (`ChatHub.java:704`), so duplicate done events are harmless, but a duplicate `buddy_error` adds a second ERROR bubble (`:679-684`). Existing code already suppresses double errors (agy/grok `status=0` when the agent reported its own error `:970-ish`, `:950-ish`); status 143 is also skipped (`:989`) so Stop doesn't show an error.
- App-side: UI state is touched on the main thread (`main.post`); timers via `main.postDelayed`. `ses.running` cleared only in `buddy_done` and the give-up path; `Prefs.setBusy`, `StepLog`, `Background.close` all hang off `runEnded`, so any new ending path must call `runEnded(ses)`, set `outcome = "failed"`, add an ERROR bubble, and clear `status`.
- Idle-timeout hazard: legitimate long silences exist: a tool call may take 10 min (`Helpers.java:26` comment; MCP timeout 600000 in `buddy-run:363+`), local models take 15 min (`LOCAL_GIVE_UP_MS`), approval cards wait on the user. "No event for N minutes" must be gated on "no live pid" (as the brief says) or N >= 10 min+, and `onToolActivity` already refreshes `lastEventAt` for all running chats (`ChatHub.java:550`).
- Version: any `buddy-run` change needs `HELPER_VERSION` bump and CI job `helper-tests` must stay green; `run.sh` fixtures compare sorted JSON, so new event types in the stream path would need fixtures/expected updates.
- The app can read the pid file only through the Linux root path; checking liveness from Java means reading `/proc` of the proot guest from outside (unverified whether `/proc/<pid>` of guest pids is visible to the Android app process; proot translates paths, pids are real kernel pids but guest `$S/pid` contains the real pid as seen inside proot, likely equal). Safer: have the helper do the checking (a watchdog in buddy-run, or an `alive <session>` command) and let the app call it via `Helper.run`, or use the `Helper.run` Process exit as "helper gone" signal (unverified viability: `Helper.run` doesn't currently expose the Process to ChatHub).
