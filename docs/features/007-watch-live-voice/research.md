# Research: 007-watch-live-voice
<!-- Researcher, 2026-11-15 (claude-sonnet-5-5). Sources on every claim. -->

## Summary
- **Both halves hinge on one fact: Buddy's ChatGPT voice never exposes audio to Java.** `CodexLive` and `CodexSpeech` use a hidden WebView doing WebRTC: mic in via `getUserMedia`, voice out via an `<audio>` element on the phone (`CodexLive.java:624-710`, PAGE `:826+`; `CodexSpeech.java:241-271`). The only Java-visible audio is the optional own-mic fallback (`AudioRecord` 16 kHz mono, pulled by the page, `CodexLive.java:748-813`). So watch audio needs a new transport, not a thin relay.
- **A PCM transport exists in Codex's app server, marked EXPERIMENTAL.** `thread/realtime/start` accepts `transport: {type:"websocket"}` besides `webrtc` (and `existingCall`); `thread/realtime/appendAudio` takes `{threadId, audio:{data(base64), numChannels, sampleRate, samplesPerChannel?}}`; the server emits `thread/realtime/outputAudio/delta` with the same chunk shape (schema from `codex app-server generate-json-schema --experimental`, codex-cli 0.169.0 on this phone, 2026-11-15). Buddy does not use any of these today (`grep` only finds the string in `CodexLive.java:445`, as a log filter). Not tried: audio sample rate/format of the output, whether `websocket` works with `clientManagedHandoffs`/`prompt`/`voice` like the webrtc path, and whether webrtc also emits output deltas (unverified; `live.log` has 0 lines because `notification()` skips logging them, `CodexLive.java:445`). **First Coder task: a probe of websocket transport (rates, latency, handoffs).**
- **Fallback if websocket is unusable:** run the call on the phone as now and bridge the WebView's audio: mic side already has `ownMic`/`pull` (page pulls PCM from Java; Java would pull from the watch instead of `AudioRecord`); the voice side would need the page to forward decoded audio to Java (AudioWorklet/ScriptProcessor → `@JavascriptInterface`) (unverified; same idea as the existing `ownTrack` in reverse).
- **Phone-lock trap (done-when 1 "phone locked works"):** a live call ends on `ACTION_SCREEN_OFF` (`CodexLive.java:207-212`, string `live_ended_screen_off`) and when Buddy is paused/stopped (`BuddyService.java:587,652`). A watch call must be exempt from the screen-off rule (a flag on the call: `fromWatch`), and the process/WebView must stay alive with the screen off (needs a wake lock + foreground service on the phone; the existing `buddy:watch` wake lock is 15 min, `WatchLink.java:33,167`). WebView/WebRTC in a locked phone is unverified; the Codex-websocket path avoids the WebView entirely.
- **Phone mic conflicts:** `CodexLive.start` stops phone listening/speaking, requires `Voice.micAllowed`, and `Voice.listen` refuses while a call is on (`Voice.java:101`). A watch call must not open the phone mic or play on the phone speaker; `AudioRoute.use` (`CodexLive.java:189,696`) would put the phone in communication mode — skip for watch calls (unverified effect).
- **Agent plumbing is reusable as is.** `utterance()` sends the voice's transcribed words to the chat as typed (`CodexLive.java:523-556`); `agentSaid/agentWaiting/agentDone` are called from `ChatHub` (`ChatHub.java:638,646,672,683,711,981`) and `tell()` feeds the voice via `thread/realtime/appendText` (`CodexLive.java:417-440`). Only the audio endpoints move to the watch. The call is keyed on a `Sessions.Session` (`ses`), one call at a time, static singleton.
- **Watch side has no mic code or permission yet.** `wear/src/main/AndroidManifest.xml` has no `RECORD_AUDIO` and a foreground service of type `remoteMessaging` only (`:5-8,49-52`); a mic stream needs `RECORD_AUDIO` (runtime prompt on watch) + `FOREGROUND_SERVICE_MICROPHONE` and `foregroundServiceType="microphone"` (standard Android 14+ rule, not fetched: unverified). Watch TTS in `Talk.java:285-368` (`TextToSpeech`, `USAGE_ASSISTANT`).
- **Part (b) today:** watch reply text is cleaned on the phone (`Voice.spoken`) and sent over `/buddy/reply` (`WatchLink.java:131-137`); `Talk.say` speaks it with the watch `TextToSpeech` (`Talk.java:~270-290`). The phone's ChatGPT voice is chosen by `Prefs.speechEngine == "chatgpt"` + `SetupState.planSignedIn(c,"codex")` with `Prefs.speechVoice` (`Voice.java:239`, `Prefs.java:~763-776`) and has a Fallback callback (`CodexSpeech.java:36,53`). `CodexSpeech.speak` plays on the phone and reports no audio; it is one-text-at-a-time with a queue (`CodexSpeech.java:26,139`).
- **Cost model inputs (for the plan's required efficiency statement):** measured on the phone's real calls, WebRTC (Opus) carries ~1-4 KB/s up and ~0.1 KB/s down when idle (`~/.buddy/live.log` "rtp 10 s: sent 10625 B / 37698 B / 17872 B; got 210-1020 B per 10 s"). Raw PCM16 mono 16 kHz is 32 KB/s each way (24 kHz = 48 KB/s). MessageClient is capped at 100 KB per message and unreliable; ChannelClient is the stream path (Data Layer docs, see 003 research). No battery measurement exists; can be estimated or measured with `adb shell dumpsys batterystats` on the Watch4 (Wi-Fi adb works, 003 verify.md).

## Prior art
- **Codex app-server realtime API** (local schema, codex-cli 0.169.0, generated with `codex app-server generate-json-schema --experimental --out DIR`): transports `websocket | webrtc{sdp} | existingCall{callId}`; requests `thread/realtime/{start,stop,appendAudio,appendSpeech,appendText,listVoices}`; notifications `thread/realtime/{started,sdp,itemAdded,item/started,item/completed,item/transcript/delta,transcript/delta,transcript/done,outputAudio/delta,error,closed}`. `ThreadRealtimeAudioChunk = {data:string, numChannels:u16, sampleRate:u32, samplesPerChannel?:u32}`; start params include `clientManagedHandoffs`, `voice`, `prompt`, `outputModality`, `version`. Marked EXPERIMENTAL, so it can change with a Codex update (Buddy bundles/uses whatever `codex` is installed: `/root/.local/bin/codex`).
- Wear Data Layer: `ChannelClient` for streams (no persistence), `MessageClient` for small commands (003 research, https://developer.android.com/training/wearables/data/channels not re-fetched today (unverified details of throughput/latency)).
- Other watch voice apps: OpenClaw's `wear/` module records on the watch (foreground service microphone, `RECORD_AUDIO`) per 003 research; none relays to a Codex voice.

## Constraints and risks
1. **Experimental API**: websocket transport and `appendAudio` are experimental; an unattended Codex update can break the watch call. The WebRTC path (existing) is the stable one. Mitigate by a clear error and no change to the phone call.
2. **Audio format/latency unknown** until probed: output rate (likely 24 kHz PCM16, unverified), input rate accepted, jitter over Bluetooth ChannelClient. Voice-to-voice latency adds phone↔watch hops (BT) to the round trip; BT is the default path, Wi-Fi fallback (003 research).
3. **Echo**: with the watch mic and watch speaker 3 cm apart, the voice hears itself. The phone path uses the WebView's AEC / `VOICE_COMMUNICATION` source with `AcousticEchoCanceler` (`CodexLive.java:749-770`). Watch: use `AudioSource.VOICE_COMMUNICATION` + AEC if the Watch4 has it (unverified), else half-duplex (mute mic while the voice plays) — interrupting then impossible.
4. **Screen-off ends calls** (see Summary): must be bypassed for watch calls, and the 5 min idle / 30 s connect watchdog still apply (`CodexLive.java:297-311`); the watch's `Talk` wait ceiling is 15 min.
5. **Single call and single mic**: `CodexLive` is a static singleton; a watch call and a phone call are mutually exclusive. `Voice.listen` and phone read-aloud must not run; `CodexSpeech`/`Voice` read-aloud on the phone would double the speech if `Prefs.speakReplies` is on (`ChatHub.add` speaks unless live, 003 research item 13) — a live call has the carve-out `ChatHub.java:~985` for live calls; a watch call must hit the same carve-out.
6. **Battery (watch)**: mic capture + speaker + radio streaming 32-48 KB/s keeps the watch CPU/radio busy for the whole call (foreground service + partial wake lock). Expect much more drain than one-shot text + TTS; not measured. Part (b) costs: the phone's WebRTC voice call is opened per reply batch (`CodexSpeech` connects, ~seconds, then closes when idle `watchdog` `:179`) and the audio (PCM or Opus) goes to the watch; the watch TTS alternative runs on-device. Net: (b) moves synthesis to the cloud/phone and adds ~32-48 KB/s of BT while it speaks (a 20 s reply ≈ 0.6-1 MB) plus connect latency of a fresh call (several seconds, `CODEX connect` times in `live.log`: unverified). Measure on the Watch4 with `dumpsys batterystats`/`dumpsys battery` before/after; the Verifier must state it (done-when 3).
7. **Doubled speech risk in (b)**: the watch must speak once, either streamed phone audio or its own TTS ("with it off or failing, the watch TTS speaks it, once"): partial audio then failure → no re-speak of the already played part (see `CodexSpeech` "a text the voice already started isn't read again", `:208`).
8. **Permissions**: watch `RECORD_AUDIO` runtime prompt (watch screen); `FOREGROUND_SERVICE_MICROPHONE` for background capture. Start from an on-screen action only (Android 14+ restricts starting a microphone FGS from the background; unverified).
9. **F-Droid**: any Wearable/Play code stays in `src/watchlink` + `wear/` (decision 2026-11-15, 003). New phone-side audio relay must too, but `CodexLive` changes (hooks for a non-WebView audio sink) are in `main` and must not reference Play services; a small interface in `main` implemented in `watchlink` is the pattern (cf. `Flavor.java`, unverified how 003's WatchLink calls into main: it just calls package-private ChatHub from `app.buddy.assistant`).
10. **Max message/stream**: MessageClient 100 KB cap and no ordering/retry guarantee (003 research); audio must use ChannelClient (input/output streams, Bluetooth) — channel open/close and `ChannelClient.ChannelCallback` semantics not re-read (unverified).
11. **Fork/upstream**: changes to `CodexLive` raise merge friction with upstream's file; keep the diff small (additive hooks) (upstream sync is a separate feature, brief non-goal).
