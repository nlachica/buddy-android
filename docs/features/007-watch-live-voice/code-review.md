F1 [major] Closing a voice channel can crash the watch during fallback - `wear/src/main/java/app/buddy/assistant/wear/Talk.java:491`: `voiceClosed()` iterates the live `toSay` ArrayList and calls `toTts()`, which calls `pump()` and removes converted items from that same list (`:451-459`, `:367-379`). For a single uncommitted reply with TTS ready, a phone cancellation/disconnect converts and removes the sole item; the enhanced-for iterator then advances against a modified list and throws `ConcurrentModificationException` on the main thread. The required link-failure fallback can therefore kill Talk instead of speaking reliably. -> Return immediately after converting the matching id (as `sayItself()` already does), or iterate a snapshot. Exercise channel closure before first sound with one reply and with several queued replies.

F2 [major] Cancelling the only connecting reply leaves an empty realtime call alive - `app/src/main/java/app/buddy/assistant/CodexSpeech.java:112-117`: before the speech connection completes, the reply is still in `queue` and `current` is null. Hushing it or losing its channel takes this branch, removes the item, and returns without closing the WebView. If the connection then succeeds, `connected()` calls `next()`, which returns for the empty queue. The watchdog (`:294-318`) has no connected/idle/empty exit: all reading branches are false and the connection deadline no longer applies. The WebRTC session and 200 ms watchdog continue until an unrelated stop or server closure, wasting phone resources after the watch has stopped listening. -> When cancellation leaves no current item and no queued items, retire/close the connection with the same stale-session isolation used for current-item cancellation. Check cancellation of the sole queued item during setup, followed by a late connected callback, and verify that another queued or current phone item is preserved.

F3 [major] A delayed old call header can terminate the newer watch call - `app/src/watchlink/java/app/buddy/assistant/WatchCall.java:76` and `:106-116`: every channel has its own reader thread, but `begin()` accepts every parsed header and calls `CodexLive.start()` without checking call generation. A valid interleaving is: reader A parses its header and pauses before posting `begin`; the watch ends A and starts B; B's reader posts and starts B; A resumes and posts its old `begin`, which ends B through `CodexLive.start()`. A then observes its already closed input and hangs itself up. B receives a correctly tagged end for B and stops, so the watch's id filter cannot save it. Also, the `finished` guard runs only after starting/replacing the live call. -> Reject retired/older requests before calling `CodexLive.start`, using the node and call generation, and check finished/closed state before any start side effect. Verify with deliberately delayed delivery of A's begin after B has started; B must retain its call, chat flag, and wake lock.

F4 [major] First-sound ownership and TTS fallback are not atomic - `wear/src/main/java/app/buddy/assistant/wear/Talk.java:452-458` and `:406-407`, with `wear/src/main/java/app/buddy/assistant/wear/Speaker.java:116-127`: `volatile committed` makes the flag visible but does not serialize the decision. The main thread can read `committed == false` in `toTts`, then the Speaker thread writes the first audible block and sets it true, then the main thread stops the stream and queues the entire text for TTS anyway. A /say or head timeout racing the first sound can therefore replay the beginning in the other voice, violating done-when 2. -> Give first audible output and fallback one shared, atomic ownership transition, including preventing audible writes after fallback wins; a later unconditional volatile assignment is insufficient. Exercise both orderings around the first audible write and assert that exactly one output owns the reply.

F5 [major] Microphone read failure leaves a live but unusable call - `wear/src/main/java/app/buddy/assistant/wear/Call.java:239-240`: a negative `AudioRecord.read()` result only breaks the loop. `mic()` and then `talk()` return normally, so the exception cleanup path is bypassed and neither `finish()` nor `Run.close()` runs. The UI remains connected, the channel/speaker and recorder remain owned, and the foreground service/wake lock stay up while no more microphone audio can reach Buddy (until another end condition eventually fires). -> Treat a negative read while the run is alive as a microphone failure and post identity-checked finish/cleanup, or throw into the existing failure path. Verify a read error releases the recorder, channel and wake lock and ends the phone call; a read interrupted by an intentional close must not affect a replacement run.

F6 [minor] Remote calls still apply the phone's selected audio route - `app/src/main/java/app/buddy/assistant/CodexLive.java:746`: only the start-time `AudioRoute.use()` was guarded. The connected callback still invokes it for a watch call, although plan Design (a) explicitly excludes both calls. `AudioRoute` can select the phone's configured communication device and keeps polling throughout the remote call despite the audio belonging to the watch. -> Guard this invocation with `remote == null` as well; check the watch-call path with a non-default phone audio-device preference.
