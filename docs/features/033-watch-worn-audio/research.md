# Research: 033-watch-worn-audio
Date 2026-11-21. Researcher: claude-sonnet-5-5.

## Summary
- Auto picks the watch in ONE function: `AudioRoute.pick(saved, savedHere, headset, watch)` (`AudioRoute.java:~95`). Its `watch` arg is just `WatchVoice.link() != null` (build has the link), so today "watch" = github build, not worn, not even reachable. Everything (read-aloud, Live, settings text) funnels through it via `target()` / `liveTarget()` / `autoNow()`.
- The "reachable" check is separate and async: `WatchVoiceLink.find()` asks the Data Layer capability `buddy_watch_read` with `FILTER_REACHABLE` (3 s timeout), `WatchVoiceLink.java:~42`. No cached state on the phone.
- Callers of the watch decision: `ReadQueue.start` (`ReadQueue.java:~175-190`, via `Out.watchWins()` = `KEY.equals(AudioRoute.target(app))`, `WatchVoice.java:100`), `LiveWatch` (`watchWins()` = `AudioRoute.liveTarget`, `LiveWatch.java:407`; re-polled every 500 ms in `poll`/`decide`), `Voice.speak` (`Voice.java:338`, `quiet` = Watch not hand-picked), `SetupActivity.autoAsk` (`:132`, every 5 s) and `SettingsTool.audioNow` (`:~420`).
- Adding a worn gate inside `pick()`'s `watch` input (or at `target()`/`liveTarget()`/`autoNow()`'s `link != null` arguments) covers all of the above; explicit Watch pick returns early on `savedHere` (`pick` line 1), so it stays unchanged.
- No worn-state message, no sensor code and no sensor permission exist in `wear/` today (grep for BODY/sensor in `wear/src`: no hits).
- Data Layer: wear -> phone is JSON `MessageClient` messages, paths `/buddy/*`, received by phone `WatchLink.onMessageReceived` switch (`WatchLink.java:72-100`, manifest filter `pathPrefix=/buddy`). A new `/buddy/worn` message needs a new `case` and a path constant on both sides (`wear/.../Phone.java:15-20`).
- Sensor: `TYPE_LOW_LATENCY_OFFBODY_DETECT` is on-change, values[0] 1.0 on-body / 0.0 off-body, initial event on registration. Wake-up and permission need on-device checking (see below).

## Lifecycle facts (watch)
- Watch services are started on demand: `ReadAloud` by `CHANNEL_EVENT`, `Talk`/`Call` by the UI. Nothing runs continuously; a sensor listener needs an owner. Options to be chosen by Planner: a `WearableListenerService` can't hold a listener long (system kills it after the callback); a persistent listener needs a foreground service (visible notification, battery) or a registration while a short-lived component is alive. Cheapest fit for "report on change and at start/reconnect": report on demand when the phone asks (phone sends `/buddy/worn?` message, watch registers sensor, waits for the initial event ≤5 s, replies, unregisters) — avoids a permanent service but adds latency to `find`. (Design note, unverified; Planner decides.)
- Phone is the one that decides at use-time (Auto is evaluated at each reading/call and every 500 ms–5 s in polls), so a cached `{worn, timestamp}` on the phone (statics in `WatchLink`/new class in main, read via `WatchVoice.Link`) keeps `pick()` synchronous. `pick()` is pure and sync; `find()` is async. A pull (ask the watch) fits only async callers.

## Sensor facts (sources)
- Android doc: sensor "returns an event every time the device transitions from off-body to on-body and from on-body to off-body"; `values[0]` 1.0 on-body, 0.0 off-body; initial event within 5 s of activation; transitions within 3 s (on->off) / 5 s (off->on) — https://developer.android.com/reference/android/hardware/SensorEvent#values (read by fetch agent; the HAL original in AOSP says on->off 1 s, off->on 3 s: https://gerrit.omnirom.org/plugins/gitiles/android_hardware_interfaces/+/a02a8dcdcb896edc2d8ef35902f7b510edc1a9b4%5E%21 via search summary).
- Added API 26 (string-type constant: https://developer.android.com/reference/android/hardware/Sensor#TYPE_LOW_LATENCY_OFFBODY_DETECT). minSdk 30 is fine.
- Reporting mode on-change: AOSP HAL definition (link above). Wake-up: AOSP framework commit lists it among wake-up types (https://gerrit.omnirom.org/plugins/gitiles/android_frameworks_native/+/2e990eb59e927187b11c7b5f0abe6dbdb0123d1d%5E%21/libs, search summary). Android's public pages state neither; use `sensorManager.getDefaultSensor(TYPE_LOW_LATENCY_OFFBODY_DETECT)` (non-wakeup default) and check `sensor.isWakeUpSensor()` on device (unverified). A non-wake-up listener stops delivering while the CPU sleeps; events batch until wake.
- Permission: Android pages show none for this type. Samsung's blog says the app needs `BODY_SENSORS` — https://developer.android.com/reference/android/hardware/Sensor (heart rate needs BODY_SENSORS / health.READ_HEART_RATE on 36) and https://developer.samsung.com/sdp/blog/en/2023/06/14/detect-when-a-galaxy-watch-is-being-worn (Galaxy Watch; "mSensorManager.getDefaultSensor(Sensor.TYPE_LOW_LATENCY_OFFBODY_DETECT)", needs BODY_SENSORS per the blog). Conflict: verify on the watch whether registration works with no permission; if a runtime permission is required, wear needs a manifest entry plus a grant flow (watch has UI: `ChatsActivity`). (unverified)
- Samsung: the sensor exists on Galaxy Watch (blog above, same page; also https://developer.samsung.com/health/sensor/sample/hr-tracker.html uses the off-body sensor). Values are floats: compare `>= 0.5`, not `==`. Samsung documents an adb broadcast `force_set 1` to fake the state for testing (same blog; exact action not read, check it). A watch without the sensor: `getDefaultSensor` returns null -> send nothing / "unknown".
- Alternative not needed: Health Services has no on-body API on the pages read (https://developer.android.com/training/wearables/health-services/).

## Constraints and risks
- `pick()` signature is used by many tests (`AudioRouteTest.java:46-58`); adding a param changes all, so prefer feeding the gate through the existing `watch` boolean (callers pass `link() != null && Worn.fresh()`). `autoNow` has its own `pick("", false, headset, link != null)` call (`AudioRoute.java:~151`) and then `find`: a worn gate must be in both or the display and the route disagree.
- Live (`LiveWatch.poll` / `decide`) re-checks `watchWins()` and calls `stop()` when it flips: a worn change mid-call moves the voice back to the phone; Planner should decide if that is wanted (brief says "wherever Auto routes to the watch... not-worn skipped").
- `want()`/`liveDevice` already ignore the watch's SCO unless it is the saved pick; no change expected there.
- The watch's capability `buddy_watch_read` reachable + worn: two separate facts; stale bound must be longer than any heartbeat the watch sends; if the watch sends on change only, a long worn period gives an old timestamp — so either heartbeat (battery) or "last report is valid until a disconnect/ change" with unknown after a reconnect. Disconnect is observable on the phone via `CapabilityClient`/`NodeClient` listeners (`Wearable.getNodeClient().getConnectedNodes()`; not used by phone today).
- Phone-side state is in-memory statics: lost on phone process death -> unknown -> speaker until the watch reports again; the watch must resend at start/reconnect (brief's done-when).
- Doze/background: Data Layer messages wake `WatchLink` via Play services; F-Droid has no `WatchLink`.
- `SettingsTool.audioNow` text hardcodes "auto -> watch, or <android> when no watch answers" (`SettingsTool.java:~422`) and `SetupActivity` string `audio_...`: wording for off-wrist needs updating.
- Brief also requires CI to build both APKs; wear is a separate module with only one unit test.
