## Summary (2026-11-16)
- The launch is a plain `Context.startActivity(ACTION_VIEW, apk, NEW_TASK)` from `BuddyService` (an AccessibilityService, `AndroidManifest.xml:250-253`), made on the tool thread after the approval card is answered and the APK is downloaded: `Updates.java:169-173` called from `Tools.java:2252` (`updateBuddy`). No activity, PendingIntent or notification is involved.
- Order of events: card (overlay) -> user taps -> card removed (`BuddyService.java:~985`, `cancelConfirm` only on timeout; answer path just returns) -> status "downloading" -> HTTP download (`Updates.java:140-150`, 60 s read timeout) -> version check -> `startActivity`. By then Buddy has no activity/visible window of its own; the other app is in front. So the start is a background activity start (BAL).
- `startActivity` returning without exception does NOT mean the installer showed: BAL-blocked starts are silently dropped (logged only as "Background activity launch blocked"). The code sets `opened = true` right after the call and the tool then says "The installer is open" (`Updates.java:174-177`, `Tools.java:2262`). That is the false claim in the brief. Nothing checks the result.
- Why the 2nd call works: unverified but consistent with BAL rules. The 2nd call's first `startActivity` is the same code path; what differs is that the user has just been shown/handled Buddy-related UI (agent reply, user likely opened Buddy chat to ask again => Buddy activity in front/recent). The "works when Buddy in front" half is what the brief reports; no logcat from the failing run exists in the repo (`runs/` has only a researcher log). Cause is unconfirmed on-device.
- Permissions present: `REQUEST_INSTALL_PACKAGES` (`AndroidManifest.xml:16`), `POST_NOTIFICATIONS` (`:10`), `POST_PROMOTED_NOTIFICATIONS` (`:12`). NOT present: `USE_FULL_SCREEN_INTENT`, `SYSTEM_ALERT_WINDOW`, any foreground service (grep `startForeground|foregroundServiceType|USE_FULL_SCREEN|SYSTEM_ALERT` in `app/src/main`: no hits). compile/target SDK 36, minSdk 30 (`app/build.gradle*`).
- Notification infrastructure already exists: `Updates.notify` builds a notification with `PendingIntent.getActivity` (opens `MainActivity` with extra `update`) on channel `CHANNEL` (`Updates.java:200-226`), `cancel` removes it (`:228-230`). A PendingIntent tapped by the user is BAL-exempt (Android docs). `Updates.install` calls `cancel(c)` after "opened".
- Same pattern (and same bug) in `Tools.installApk` (`Tools.java:2214-2218`, "The installer is open") and in the in-app sheet `Updates.sheet` (`:301-326`, runs with an Activity in front so it is fine). `wait_for_install` (`Tools.java:~2100-2160`) already detects the installer on screen via accessibility windows (`installerOnScreen`, `Tools.java:2128-2140`) - reusable to verify the launch.
- Tests are Context-free JVM tests (`app/src/test/java/app/buddy/assistant/*Test.java`, e.g. `UpstreamNoteTest`, `ApkStagingTest`); the `Updates.install` Context path has no test. Feature 004 `decisions.md:230-233` records this as a known issue ("a fix would launch the installer from a notification/the bubble").

## Prior art
- Android background activity launch restrictions (developer.android.com/guide/components/activities/background-starts): exemptions include an app with a visible window, a PendingIntent from a notification the user taps, a full-screen-intent notification (needs `USE_FULL_SCREEN_INTENT`; on Android 14+ it is user-revocable for non-call/alarm apps, `NotificationManager.canUseFullScreenIntent()`), and a `SYSTEM_ALERT_WINDOW` holder with a visible overlay. Android 14 (SDK 34) tightened to opt-in for PendingIntent senders (`setPendingIntentBackgroundActivityStartMode`) and Android 15 more. Accessibility service is not on the list (unverified from memory; the Planner/Coder should re-check the page, I did not fetch it this run).
- Typical self-update flow: `PackageInstaller` session API with `Intent` callback (`STATUS_PENDING_USER_ACTION`), the system's confirm intent being launched from a notification/Activity. Installer APIs from a Service also need the user-action activity started in the foreground (unverified).
- Upstream (`ghorbelhamdi/buddy-android`) has no relevant change known to me (not checked this run).

## Constraints and risks
- Cannot reproduce here: no device logcat; Linux sandbox has no Android. Verify only on the phone on the next fork release (brief "Done when" #1). `adb logcat -s ActivityTaskManager` would show "Background activity launch blocked" but needs adb (unverified availability).
- Detecting a blocked launch: no exception, no return value. Options for detection: poll `foregroundPkg()` / `installerOnScreen()` for a few seconds after `startActivity` (needs accessibility, which Buddy has; `Tools.java:2128`), or stop claiming and always hand over via notification.
- Notification PendingIntent route: needs `POST_NOTIFICATIONS` granted at runtime (user may have denied; `nm.notify` catches `SecurityException`, `Updates.java:223`). A heads-up/tap is then one extra user tap, still "the installer opens from a tap" (fits "launch from the approval-card tap"). Full-screen-intent needs a new manifest permission and may be denied by Android 14+; on an unlocked phone it degrades to a heads-up notification anyway.
- The file `out` is deleted on failure paths (`Updates.java:176`) but "a file the installer will open later is left" - a notification route must keep the APK until tapped and clean old ones (`FilesProvider.newApk` per-attempt files; cleanup logic in `ApkStagingTest` scope).
- The approval card is Buddy's own overlay (accessibility overlay window); its tap happens ~10-60 s before the launch (download), so the "visible window" exemption is gone by then. Launching right at the tap (before download) is impossible: the APK isn't there yet; could download first, then ask - but the brief says not to change the card's wording or the flow.
- `installWaits`/`cardTouches` logic (`BuddyService.java:675`) treats the installer in front as "user's touches"; a notification-tap route should keep that working.
- Release/version bump and device test are needed per `AGENTS.md` "Updating Buddy on the phone"; verification only after tagging a fork release.
