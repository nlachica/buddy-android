## Round 1 - Code Reviewer (gpt-6.2-astra)

F1 [major] A restored message is lost if its chat's helper survived Buddy restarting - `app/src/main/java/app/buddy/assistant/Schedules.java:595` restores the wait and immediately pumps it. A cold `ChatHub` marks the old chat interrupted with `running == false` even though its Linux helper can survive the app process (`ChatHub.java:76`, `McpServer.java:71`). The pump clears the pending occurrence at `Schedules.java:435`. The asynchronous helper then refuses the new message with `BUSY` (`linux/buddy-run:341`), which `ChatHub.java:378` ignores. Nothing retries when the old helper finishes. -> Keep the occurrence recoverable until the helper accepts it, or reconcile the surviving helper before dispatch. Test a restored chat whose helper reports busy and then exits. The due message should start once.

F2 [major] Saving an unchanged Schedule drops the run already due - `app/src/main/java/app/buddy/assistant/ChatHub.java:542` clears the pending run on every save. The editor calls this method even for an unchanged plan or a change to the quiet option alone (`ChatActivity.java:1815`). A user who opens the waiting 08:00 schedule and presses Save can lose today's run. The edit test removes the key itself at `SchedulesWaitTest.java:121`, so it cannot catch this. -> Compare the old and new message and timing before replacing the plan. Preserve the occurrence for an equivalent save or a quiet/wake change. Test the production transition for both an unchanged save and a genuine replacement, including what runs when the chat becomes free.

F3 [major] A waiting Schedule can take over the previous run's watch or notification-rule session - `app/src/main/java/app/buddy/assistant/Schedules.java:430` allows a waiting recurring run to start the moment its chat becomes idle. The scheduler listener calls `pump()` synchronously at line 578, during delivery of the previous run's completion. For a watch request, `WatchLink.java:347` sees the chat running again and keeps forwarding the scheduled reply as part of the watch request. For a bound notification rule, if the scheduler listener runs first, `Triggers.java:336` sees the same busy state and keeps the old rule active for the scheduled run. -> Let completion listeners and their posted end checks finish before starting waiting work in the same chat, or tie their cleanup to the completed run ID. Add a handoff test that ends a tracked run with a recurring Schedule waiting. The previous run should close and the scheduled run should start once under its own settings.

F4 [minor] Restart extends the documented one-hour offline wait - `app/src/main/java/app/buddy/assistant/Schedules.java:487` gives every restored ID a fresh hour. A recurring task waiting offline from 08:00 can restart at 08:55, remain offline through 09:00, and still run when connectivity returns at 09:30. The guide promises an hour at most, while the plan explicitly allows an old restored run. -> Preserve the original expiry for bounded waits, or document the fresh hour after restart if that is the intended exception.
