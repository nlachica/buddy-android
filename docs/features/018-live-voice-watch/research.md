## Summary
- **Bug fix is one function.** `AudioRoute.want()` returns `""` for `watch` (`AudioRoute.java:191-194`), so `reconcile()` hits `drop()` (`:209-211`) → `clearCommunicationDevice()` (`:249`) while the WebView keeps `MODE_IN_COMMUNICATION` (`dropMode` skips it during live voice, `:256`) → earpiece (diagnosis.md). The poll runs `reconcile` every tick while `CodexLive.on()` (`:266-270`).
- **A speaker key needs no new lookup logic.** `reconcile` already matches `key(i)` (`type:productName`, `:217`, `:~275`) against `am.getAvailableCommunicationDevices()`; `label()` already knows `TYPE_BUILTIN_SPEAKER` (`:147`). `want()` can return the key of the built-in speaker found in that list while `CodexLive.on()`. A headset must still win per 016: `pick()` (`:86-90`) returns a saved key first, so a picked Watch is returned as `watch` even with a headset. The planner must decide whether Watch-during-live with a headset connected → headset or speaker (brief: "a connected headset keeps priority"). Android's own communication-device choice with no pick favours earpiece, which is the bug; the headset case is not tested anywhere (`AudioRouteTest.java` has `headsetTypes/headsetIn/autoOrder/pickedDevice/settingsRead…`, all pure functions, no `want()` test: it needs a Context).
- **Live voice on the watch already has most of its parts (007).** `CodexLive.Remote` (`CodexLive.java:80-91`) + `start(c, s, Remote)` (`:208`) + `WatchCall` (`app/src/watchlink/.../WatchCall.java`) + `PcmOut` + the page's `Buddy.remote()` / `tap()` of the voice to Java (`:707-718`, `:952-956`, `CodexSpeech.TAP_JS`). But `Remote` is all-or-nothing: with a Remote the page opens no mic (`ownMic` takes watch audio via `push`, `:693-694`), mutes the page's `<audio>` (`out.muted = rem`, `:952`), skips `AudioRoute.use` and the screen-off receiver (`:211, :221`). Calls are **watch-initiated**: the watch opens channel `/buddy/live`, writes a header, sends mic PCM (`WatchCall.java:64-98`).
- **Voice-only-to-watch is a new combination** (phone mic + page AEC, watch speaker): needs a second mode of `Remote` (e.g. a flag/second method: `remote()` true for output only), with mic path `getUserMedia` as today, `out.muted` true, `tap` active, and `AudioRoute`/screen-off rules kept (phone mic is open, phone must stay awake as today). Nothing in the page JS supports this split today (`Buddy.remote()` drives both mic and mute at `:927` and `:952`). Echo is not a concern: the watch speaker is away from the phone mic (reasoning, unverified on device).
- **The watch receiver for phone→watch audio already exists**: 012's `ReadAloud` (`wear/.../ReadAloud.java`) plays PCM16 mono 16 kHz from a phone-opened channel `/buddy/read/<id>` through `Speaker`, with codes `NOT_PLAYED=1` (busy/refused/silent/failed), `PLAYED=2`, `0` (broke after sound). Phone side `WatchVoiceLink` (capability `buddy_watch_read`, `PATH=/buddy/read/`, `READ_CAP = 10 min × 32 KB/s`, `WatchVoiceLink.java:23-25`) and `ReadStream` implement `ReadQueue.Stream` (`ReadQueue.java:19-22`). A live call is open-ended, while a reading is capped at 10 min and ends with `finish`. Reuse = one long-lived `/buddy/read/<id>` channel written by a `Remote.pcm` that never calls `finish` until the call ends; unverified: 10-min cap, the `ReadAloud` wake lock `WAKE_MS = 11 min` (`ReadAloud.java:22`) and `ReadStream` abandon timers would cut a long call. 007's `WatchCall` caps at 30 min (007 decisions).
- **Watch busy rule is a trap**: `ReadAloud.busy()` = `Talk.busy() || Call.on || TalkActivity.dictating()` (`ReadAloud.java:38-40`), so a phone-live stream opened while the watch is in its own Talk/Call is refused with code 1 → fall back to phone loudspeaker (matches brief).
- **Mid-call drop fallback**: `PcmOut` has `onBroken` (`WatchCall.java:40`) for a dead stream; there is no existing path that flips an already running page from watch to phone speaker. The page's `<audio>` is muted at `ontrack` time (`:952`); un-muting mid-call would need a new `@JavascriptInterface` or `evaluateJavascript` call (not present, unverified how the page is driven: see `web.evaluateJavascript` uses in CodexLive, not read). Because `out.muted` is set once in `ontrack`, the planner can instead keep the audio element unmuted always and rely on the phone speaker as the safe default while the watch stream is only an added copy? That would double the voice — rejected by brief; so a runtime mute toggle is required (unverified feasibility, should be a JS global `out.muted = …` via `evaluateJavascript`).
- **ChatHub carve-out**: read-aloud is skipped while `CodexLive.on()` (`ChatHub.java:1057-1059`), so no double speech from 012's read queue; no change needed.
- **Tests/CI**: JVM tests exist for `AudioRoute` pure functions (`AudioRouteTest.java`) and watchlink pure classes (`PcmOut`, `ReadStream` are Google-free by design: `PcmOut.java` javadoc). `want()` takes a Context, so the speaker-key selection should be a pure function over `int type + name` lists to be testable (as `headsetIn` is). CI/ build commands: see 007/012 research (`.github/workflows/build.yml`, `helper-tests`; not re-read today).

## Constraints and risks
1. API < 31: `use()` returns early (`:166`), so on older phones neither the bug nor its fix applies (earpiece fix is a no-op there; unverified whether older phones show the symptom).
2. `reconcile` forces `other = true` for modes other than NORMAL/IN_COMMUNICATION (`:214`); a real phone call stays untouched. Fix must keep that.
3. `use()` resets `applied = null` only `if (!want(a).isEmpty())` (`:179`): with `want()` becoming non-empty during live, a mid-call Watch pick re-applies the speaker; when the call ends `want()` returns `""` again and `afterLive`/`drop` clear it (brief "ending the call restores normal mode"). The WebView's own teardown also clears device then sets NORMAL (comment `:238-239`); check no double clear.
4. The page re-picks the earpiece each time it opens the mic (diagnosis: 17:45:50.881 earpiece, Buddy put speaker back 0.8 s later via `AudioRoute.use` from the bridge `:746`); for a watch-speaker call the speaker fallback still depends on that bridge call staying (r==null case).
5. Watch speaker + phone mic mode: if the phone stays in `MODE_IN_COMMUNICATION` with the page's audio muted, other apps' audio is also in communication mode and the speaker route is irrelevant for the call; routing still matters until the watch takes over or fails.
6. `ReadAloud` limits: 10-min `READ_CAP`, 11-min wake lock, `ReadStream` abandon timers — a long call exceeds them (verify `ReadStream` code before reuse; not read in full today). Any new path name/handshake needs a watch app update: the watch is a separately installed APK (wear build, 003) — phone and watch builds must ship together; an old watch would answer code 1 or not at all, so the fallback to the phone speaker must be timed (3 s find + 10 s open, per diagnosis §1).
7. F-Droid/`build.sh` builds: no watch link; watch-specific code stays in `src/watchlink` + a main-side interface (`WatchVoice.Link` reflection pattern, 012 decisions). `CodexLive` is an upstream file: keep the diff small (007 decision).
8. Auto during live voice has the same earpiece default; changing it contradicts 001 ("Auto as before") — user decision per diagnosis; brief non-goal says Auto's order isn't changed, but Auto→watch when no headset and a reachable watch is in scope (016 `pick`).
9. Battery/cost on the watch: one-way 32 KB/s PCM for call length, not measured; same order as 012 readings (007 research item 6).
