# Research: 003-wear-companion
<!-- Researcher, 2026-11-15 (claude-sonnet-5-5). Sources on every claim. -->

## Summary
- **The phone app has zero dependencies today** (no `dependencies {}` block in `app/build.gradle.kts`; Java 8, no XML layouts, `android.useAndroidX=false`, `android.builtInKotlin=false` in `gradle.properties`). `play-services-wearable:20.0.1` (latest, 2026-04-28; `maven-metadata.xml` + `.aar` last-modified) pulls `androidx.core:core:1.0.0` (its POM), so the AGP AndroidX check will want `android.useAndroidX=true` (global, affects both flavors; AGP behaviour unverified here, not built). Plan must handle this and prove `assembleFdroidRelease` is still byte-identical (CI reproducibility step, `build.yml`).
- **Flavor mechanism to reuse**: `githubImplementation(...)` plus a `app/src/github/` source set and manifest (flavors `github`/`fdroid`, `app/build.gradle.kts:46-50`; per-flavor `Flavor.java` already exists, `app/src/{github,fdroid}/java/app/buddy/assistant/Flavor.java`). fdroid then has no gms on its classpath. Side effects: `build.sh` (on-phone, no Gradle, javac against android.jar only) compiles `app/src/$FLAVOR/java` (`build.sh:~43`), so any Play-services class in `src/github/java` breaks `FLAVOR=github ./build.sh`. Keep the Play-services code out of `build.sh`'s reach or accept it (decision for Planner).
- **Wear module**: `include(":wear")` in `settings.gradle.kts` (currently only `:app`); `repositoriesMode FAIL_ON_PROJECT_REPOS` with `google()`+`mavenCentral()` already fine for gms/androidx. Wear module needs its own signing config (the release config is defined inside `:app` only, `app/build.gradle.kts:32-41`, from env `BUDDY_KEYSTORE*`).
- **Data Layer hard rule**: same package name AND same signing certificate on phone and watch app, or Play services refuses to deliver (https://developer.android.com/training/wearables/data/accessing, "Security of communications"). So wear `applicationId = "app.buddy.assistant"` and signed with the same release keystore in CI (GitHub secrets `BUDDY_KEYSTORE_BASE64`, `build.yml`). Unsigned CI artifacts (no secrets, e.g. PRs) will not talk to each other.
- **Messaging fit**: `MessageClient` = no persistence, no retry, no >100 KB, Bluetooth preferred with Wi-Fi fallback, doesn't work offline (docs table, https://developer.android.com/training/wearables/data/messages). Fine for small text commands/replies; unreachable phone = send fails, so the watch must show a clear error (Done-when #4). `ChannelClient` (stream, no persistence) is the documented path for later audio (phase 2).
- **Speech on the watch is the riskiest unknown.** Official doc: free-form speech via `RecognizerIntent.ACTION_RECOGNIZE_SPEECH` + `startActivityForResult`; Voice Actions/Assistant App Actions unsupported except China (https://developer.android.com/training/wearables/apps/voice). Galaxy Watch4 reports: `SpeechRecognizer.isRecognitionAvailable()` false / "no selected voice recognition service" (Samsung forum https://forum.developer.samsung.com/t/recognitionlistener-samsung-galaxy-watch-4/20771; Stack Overflow mirrors, 2022-2023). Samsung's reply: not Samsung-specific, any newer Wear OS watch. Never tested on Nicholas's watch: **first Coder/Verifier action must be a probe on the real watch** (`isRecognitionAvailable`, `resolveActivity(ACTION_RECOGNIZE_SPEECH)`, TTS engines). Fallback designs: phone-side transcription (watch records audio via `AudioRecord`/MediaRecorder, `ChannelClient` to phone; Buddy already has `MicServer`/Claude/Codex dictation for audio→text) or a Whisper-style cloud call (WristAssist does record-then-Whisper, `InputWhisperActivity` uses `MediaRecorder`; why it avoids the recognizer is unverified).
- **Phone side hooks exist and are small**: `ChatHub.get(ctx).send(session, text)` returns an error string or null (`ChatHub.java:232,64`); all ChatHub use is on the main thread (class doc `ChatHub.java:14`); replies arrive via `ChatHub.Listener.onMessage` (`ChatHub.java:16-20`, fired from `add()` ~`:985`); run end is `buddy_done` → `runEnded` (`ChatHub.java:~700`). `Schedules.java:~495-527` is a precedent for a non-UI component registering a `ChatHub.Listener` and acting when `ses.running` goes false.
- **Install on watch from the phone**: Buddy's Linux already installs `android-tools-adb@edge` from Alpine edge/community and runs adb with its own server (`Background.java:44,575-581`). Watch needs same Wi-Fi as the phone, Developer options → ADB debugging + Wireless debugging, `adb pair ip:pairport` (code from watch), then `adb connect ip:connectport` (different port) (https://developer.android.com/training/wearables/get-started/debug-wifi, https://developer.samsung.com/sdp/blog/en/2024/04/30/connect-galaxy-watch-to-android-studio-over-wi-fi). Pairing is required on Wear OS 4+ Galaxy Watch (plain `adb connect` stopped working, Samsung Community thread 2023-11, https://eu.community.samsung.com/t5/wearables/adb-over-wifi-on-gw4-bt-with-wear-4-0-no-longer-possible/m-p/8179384). Watch4 can be on Wear OS 3 → 6 (Wikipedia "Samsung Galaxy Watch 4"), so minSdk 30 (Wear OS 3) is the floor.
- **Prior art exists, none reusable wholesale**: standalone ChatGPT-on-watch apps (WristAssist, Java, Apache-2.0), and phone+watch OpenClaw (`yuga-hashimoto/openclaw-assistant`, MIT, `wear/` module). None is Buddy's protocol.

## Prior art
- **Data Layer docs** (current as fetched 2026-11-15): clients `DataClient` (persistent, synced, Assets for >100 KB), `MessageClient` (RPC-ish, not persisted), `ChannelClient` (streams/files); capability discovery `CapabilityClient.getCapability(name, FILTER_REACHABLE)` (https://developer.android.com/training/wearables/data/messages); background receive by extending `WearableListenerService` (declared in manifest; Play services binds it when events arrive) vs. `addListener` for short-lived components (https://developer.android.com/training/wearables/data/events). Official sample: https://github.com/android/wear-os-samples (`DataLayer/`: phone `Application` + `Wearable`, uses all three clients). Reference says short-lived components should prefer `addListener` over the service (search summary of https://developers.google.com/android/reference/com/google/android/gms/wearable/WearableListenerService; page not read in full).
- **Capabilities**: phone app advertises a string via `res/values/wear.xml` array `android_wear_capabilities` (standard; standard docs page not fetched, unverified); watch finds reachable nodes with it, picks the phone node, sends to `node.getId()`.
- **Library versions** (queried 2026-11-15 on `https://dl.google.com/dl/android/maven2/...maven-metadata.xml`, same data as maven.google.com): `com.google.android.gms:play-services-wearable` 19.0.0 → **20.0.1** (latest, 2026-04-28; minSdk 23 per its manifest; deps: play-services-base 18.5.0, basement 18.9.0, tasks 18.2.0, androidx.core 1.0.0). Docs' Setup snippet also says 20.0.1 (https://developer.android.com/training/wearables/data/accessing). `androidx.wear:wear` latest stable 1.4.0 (needed only if using its widgets; probably not for YAGNI). Compose-for-Wear (`androidx.wear.compose`) 1.7.1 stable; 1.8.0 alphas only — requires Kotlin + Compose, which this repo does not use (`builtInKotlin=false`).
- **Open source companions** (GitHub API 2026-11-15):

## Constraints and risks
1. **AndroidX flag / fdroid reproducibility**: `useAndroidX=true` is project-wide. With no androidx deps in the fdroid variant it should add nothing, but this must be proven by the existing CI compare step. Alternative that avoids touching the flag for `:app`: put gms in `:app` github only needs the flag anyway (gms POM → androidx.core). `android.enableJetifier` not needed for gms 20.0.1 (androidx deps only; unverified). Check AGP 9.4.1 behaviour in a real build (not done: no Gradle run in this research; `~/android-sdk` has only `android-36` + `build-tools`).
2. **F-Droid scanner**: F-Droid's build scanner flags non-free libs referenced anywhere in gradle files (known behaviour, unverified here); the `wear` module and `githubImplementation` lines may need `scanignore`/`scandelete` entries in F-Droid's metadata (outside this repo). Also `include(":wear")` makes the fdroid build configure the wear project; keep it from resolving gms for fdroid tasks (resolution is lazy, unverified).
3. **Signing parity**: wear and phone APK must use the same cert. CI only has the keystore when secrets exist; local/PR builds unsigned. A debug-signed pair (both debug keystores differ per machine) won't talk. Mention in docs how to install.
4. **minSdk**: wear minSdk 30 matches `app` (30) and Watch4's Wear OS 3 floor (API 30). `compileSdk` 36 is available locally (`~/android-sdk/android-36`). Wear OS 4+ requires `targetSdk` ≥ 33 for newer-store checks (Play only; not relevant for sideload).
5. **Wear manifest**: `<uses-feature android:name="android.hardware.type.watch"/>`, `<meta-data android:name="com.google.android.wearable.standalone" android:value="true|false"/>` (standard Wear OS requirement; not fetched this session, unverified). Same applicationId means a single `app.buddy.assistant` on the phone and the watch; no conflict (different devices).
6. **Speech recognition on Watch4**: see Summary; `isRecognitionAvailable` false reports; `RecognizerIntent` is the documented route and worked for others via Gboard/Google app (Android Central, title level). Samsung "Bixby"/Google Assistant are system features, not callable. Probe first. If both fail, audio must go to the phone (ChannelClient) and be transcribed there (phone-side `MicServer`/dictation engines exist but expect phone-mic input; reuse requires work), or a cloud STT key — a bigger scope and a privacy change (see `docs/PRIVACY.md`).
7. **Watch TTS**: Android `TextToSpeech` on the watch's speaker; needs an engine on the watch (Google TTS or Samsung TTS; unverified present). `RECORD_AUDIO` is a runtime permission on the watch (needs on-watch prompt).
8. **Background delivery**: MessageClient has no retry and no persistence. A reply arriving while the watch app is closed needs a `WearableListenerService` on the watch; starting an Activity/foreground speech from the background on Wear OS 3+ is restricted (unverified; background-activity-start rules from Android 10+ apply). Robust approach: keep the activity foreground (keep-screen-on) during a run, or post an ongoing notification. Watch screen sleeps by default; ambient mode handling needed.
9. **Phone side wake**: a message wakes the phone app only through the Play-services-bound `WearableListenerService`, which has a short execution window; a run lasting minutes depends on `BuddyService`/foreground state. Reuse `Schedules.holdWake`-style wake lock (`Schedules.java:~495`) or rely on the accessibility service keeping the process alive (unverified).
10. **Threading**: `WearableListenerService` callbacks arrive off the main thread; ChatHub is main-thread-only (`ChatHub.java:14`), so post to `Looper.getMainLooper()`.
11. **Busy chat**: sending to a running chat becomes a "note" (`ChatHub.java:281`) with no run-end reply; the watch should not wait forever on it (watch needs a timeout or a "still working" state). `ChatHub.GIVE_UP_MS` 180 s.
12. **Replies are multi-part**: a run can emit several BUDDY messages plus STEP lines; "what to speak" must be chosen (each BUDDY text vs. `ses.lastReply` at `buddy_done`). Tool-step and approval cards exist only on the phone (non-goal).
13. **Duplicate speech**: phone also speaks if `Prefs.speakReplies` (default false); phone Bluetooth "call relay" to the watch noted in 001 is unrelated.
14. **Security**: watch→phone commands act as the user (full agent incl. phone tools). Data Layer restricts to same package+signature (https://developer.android.com/training/wearables/data/accessing), so no extra auth is strictly needed, but chat list/reply text transit Google's channel (Bluetooth, or cloud E2E-encrypted when BT is down; same page). `docs/PRIVACY.md` and the F-Droid-vs-GitHub note may need a line (Buddy states "what leaves the phone", `README.md` security list). 
15. **adb to the watch**: pairing/connect ports are random and change; Wi-Fi must be on the watch (not just Bluetooth) and "turn off automatic Wi-Fi" in watch developer options (Samsung blog above). Buddy's adb helper is wired for the *phone's* loopback (`127.0.0.1`, `Background.java:388`), not an arbitrary LAN host, so watch install is a manual `adb pair/connect/install -s` flow run through Buddy's `phone_shell`/Linux shell, or by Nicholas — not an existing feature. Watch and phone must share a Wi-Fi network without client isolation (Android docs). 
16. **CI cost**: wear module adds a few minutes; no Kotlin/Compose means no new toolchain.
