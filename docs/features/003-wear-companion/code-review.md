## Round 1 - Code Reviewer (gpt-6-astra)

Reviewed `main...HEAD` at `8df9e37`, the brief, plan, decisions, prior plan reviews, and the touched source/build files. There were no earlier code-review findings or Coder rejections.

F1 [major] Liveness polling prevents the promised screen release - `wear/src/main/java/app/buddy/assistant/wear/Talk.java:206-220` calls `changed()` for every successful `/buddy/status` reply. `wear/src/main/java/app/buddy/assistant/wear/TalkActivity.java:141-146` treats every such notification as new progress, clears `sleepy`, cancels the screen timer and starts another 120 seconds with `FLAG_KEEP_SCREEN_ON`. A quiet run gets a status reply roughly every 30 seconds, so the screen never reaches its release deadline until the run ends or the 15-minute ceiling fires. This defeats the slow-answer/screen-release test in plan test 4 and the intended battery bound. -> Keep liveness acknowledgments separate from display activity; reset the screen deadline on the initial send/heard and actual step/reply progress, not status polling. Verify a run with successful status responses but no step/reply for more than 120 seconds: the screen flag must clear while the service continues waiting and later speaks the answer.

F2 [major] A late send callback can install a timeout after the answer already arrived - `wear/src/main/java/app/buddy/assistant/wear/Talk.java:157-161` schedules `noHeard` only in the asynchronous send-success callback; `wear/src/main/java/app/buddy/assistant/wear/ChatsActivity.java:82-85` does the same for `noAnswer`. A phone response and the local Task completion are independent callbacks: if `heard` or the chat list is handled first, removing the not-yet-installed timer does nothing, and the later success callback arms it anyway. Ten seconds later Talk falsely reports no answer and removes its receiver from a valid run; the list similarly gets replaced by an error after eight seconds. A refusal/done arriving first can also be followed by a spurious timeout while its speech drains. Neither timeout verifies that its request is still pending, and the registration/send callbacks also lack guards against completion after leaving or replacing the conversation. [MessageClient's contract](https://developers.google.com/android/reference/com/google/android/gms/wearable/MessageClient#sendMessage(java.lang.String,java.lang.String,byte[])) supplies a send Task, not ordering against a remote application reply. -> Arm the deadline before initiating the send, cancel it on response/error, and guard asynchronous completions/timeouts with the current request's active/answered state (and invalidate them on stop/replacement). Keep listener-before-send ordering. Exercise both callback orders, including a fast refusal, and a registration/send completing after the user leaves; no stale timeout or stale send should affect an ended/new conversation.

F3 [minor] The mic button does not silence replies buffered during TTS initialization - `wear/src/main/java/app/buddy/assistant/wear/Talk.java:339-342` clears `pending` and stops the initialized engine, but leaves `early` intact. If a reply arrives while TTS initializes and the user taps the mic, `TalkActivity.java:76-78` calls this method and opens recognition; `ttsInit()` then drains the old `early` replies into the speaker during dictation. This breaks the planned mic-button speech interruption and can feed Buddy's own answer into the next message. -> Clear the pre-init speech buffer in `hush()` as well as the engine queue, preserving the displayed lines. Check reply-before-init, mic tap, then successful init: the buffered reply must not speak.

F4 [minor] A rejected TTS enqueue remains counted as speech for five minutes - `wear/src/main/java/app/buddy/assistant/wear/Talk.java:290-294` adds an utterance to `pending` and ignores the return value of `tts.speak`. [TextToSpeech.speak](https://developer.android.com/reference/android/speech/tts/TextToSpeech#speak(java.lang.CharSequence,int,android.os.Bundle,java.lang.String)) can return `ERROR` when queuing fails; an engine connection failure need not produce an utterance completion callback for a request it never accepted. That leaves the reply silent and the service/notification/wake lock alive until the five-minute fallback after `done`, despite no speech being queued. -> Handle an immediate `ERROR` by removing that utterance from `pending`, showing a concise read-aloud failure, and allowing normal end/stop cleanup. Check an enqueue failure with no subsequent utterance callback: text remains visible and the service stops promptly once the wait ends.
