## Round 1 - Plan Reviewer (gpt-6-astra)

F1 [major] Make the required Composio setup concrete - Done-when 4 requires Composio to list its tools, but the device recipe writes the key alone and the risk section defers incompatible authentication to another fix (`plan.md:229`, `plan.md:241`). A bare key becomes `Authorization: Bearer ...` (`app/src/main/java/app/buddy/assistant/McpServers.java:166`). Composio's current primary documentation specifies a consumer key in `x-consumer-api-key` for clients without OAuth, and distinguishes it from a developer project key ([Consumer and Developer Project Boundaries](https://docs.composio.dev/kb/guide/consumer-project-boundaries-and-auth-selection), authentication and rotation sections, checked 2026-11-16). Thus the documented test recipe is not the documented authentication route for this endpoint. -> Specify the consumer-key prerequisite and file contents `x-consumer-api-key: <consumer key>` in the Composio recipe, using the existing custom-header support; test that this file produces the intended header without exposing its value. Keep the phone check as the required completion evidence. Any remaining incompatibility that prevents that check must stay an open requirement, rather than being declared a separate feature automatically. No OAuth implementation or new header argument is needed.

F2 [major] The stale check happens after the key has already been sent - The plan claims that including the address in the snapshot prevents the key reaching another destination (`plan.md:94`), but verification reads `currentUrl` or the mutable provider's addresses (`plan.md:119`, `plan.md:132`). In the actual gate, `s.prepare(v)` runs before the snapshot comparison (`app/src/main/java/app/buddy/assistant/SettingsTool.java:1106`, `:1109`). If an address changes while the card is open, verification can send the new key to that changed address and only then refuse to save. The existing editors really mutate these objects' addresses (`app/src/main/java/app/buddy/assistant/McpServersActivity.java:214`, `app/src/main/java/app/buddy/assistant/ApiKeysActivity.java:345`). Also, the proposed existing-key card renders only set/none plus the file/mask (`plan.md:98`, `plan.md:109`), despite the risk justification saying the destination is shown. -> Capture immutable destination strings from the exact snapshot used for the card, identify the intended destination on that card without exposing credentials, and make verification use only those captured strings. Retain the final compare-and-save guard; a pre-network stale check can additionally avoid obsolete requests but must not be followed by a fresh mutable-address lookup. Extend the stale tests to assert which endpoint receives the key, including changes during verification, rather than only asserting that store was not called.

F3 [major] Header prefixes defeat the short-secret masking rule - `mask` bases its 16-character threshold on the entire file value (`plan.md:74`), while files may contain a full header (`plan.md:153`; `app/src/main/java/app/buddy/assistant/McpServers.java:169`). For the valid input `x-consumer-api-key: abc`, the input is longer than 16 characters and its last four characters are ` abc`: the card and Changed reply expose the entire credential. `Authorization: Bearer abc` has the same problem. This violates the never-full-value requirement (`brief.md:27`) even though the existing planned 10-character raw-key test passes. -> Apply masking to the actual credential after recognizing the supported header/Bearer prefixes, or use a fixed mask for prefixed values. Ensure redaction also handles a header whose value itself starts with Bearer. Add short-token cases for custom headers and `Authorization: Bearer ...` to the card/reply and error tests. Reuse `McpServers.header` semantics rather than defining a different accepted header grammar.

F4 [minor] Spell out the successful removal branch - The `KeySetting.check` algorithm refuses removal when no saved key exists, then says "otherwise" to call `keyFrom(root, file)` (`plan.md:99`), although `file == null` is the removal representation (`plan.md:83`). Following those steps literally attempts to read a null path when removing an existing key. The later card/set methods and test table require an empty checked value instead. -> Explicitly return `""` for an existing-key removal before any file read, and require its test to assert no file access and no verification request as well as one approval and `store("")`.

F5 [minor] The promised JSON rejection has no corresponding validation - The file rules say that raw bws JSON is refused, but the specified content checks are only non-empty and no control characters (`plan.md:68`). Compact JSON satisfies both. The accepted-race rationale also incorrectly says one line under 4 KB rules out JSON stores (`plan.md:239`). -> Add the small explicit JSON-container rejection that the plan promises, with a compact bws JSON fixture and a non-echoing error assertion, or remove that promise and its use as a safety argument. Do not add a Bitwarden parser or extraction path.
