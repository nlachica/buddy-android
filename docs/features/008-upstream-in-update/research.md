- **The first merge is small.** Fork and upstream share merge-base `5d1e7f7` = upstream tag v2.3.9; upstream/main has exactly 1 commit beyond it (`f93a593` "2.3.10: approvals per chat…", 30 files, +618/-45) (`git merge-base HEAD upstream/main`, `git log HEAD..upstream/main`).

- **Version rule:** `BuildInfo.java:5-6` holds `VERSION="2.3.9-fork.4"`, `VERSION_CODE=211`. Upstream 2.3.10 has code 208 (diff of BuildInfo). New fork code must be max(211,208)+1 = 212 (AGENTS.md step 2). Merge will conflict on both lines every time; resolution is mechanical: `VERSION=<upstream>-fork.1`, `VERSION_CODE=max+1`.
- **Version compare handles the new name:** `Updates.compare` (`Updates.java:299-315`) splits on `.` and parses leading digits, so `2.3.10-fork.1` > `2.3.9-fork.4` (2.3.10 → 10 > 9). `Release.newer()` and `install()` also gate on `VERSION_CODE` of the downloaded APK (`Updates.java:~108`).
- **Upstream release detection:** `gh release list -R ghorbelhamdi/buddy-android` shows v2.3.10 (Latest, 2026-11-15T21:47Z); upstream publishes tags `v2.3.x` (`git ls-remote --tags upstream`). Upstream cadence is high (v2.3.7→2.3.10 in ~1 day), so syncs will be frequent.
- **Playbook already defines the procedure:** `pipeline-playbook/pipeline/upstream-sync.md`: sync branch from main, merge `upstream/main`, conflicts resolved by a Coder with "prefer upstream's mechanism", cross-family review (Codex), tests/CI green, confirm, PR, merge, then merge main into open `feat/*` branches. It is written for human-in-loop orchestration, not automation.

## Constraints and risks
- **Where the work runs is the main design fork.** (a) The phone agent chat (Linux tools, `gh` logged in with `repo`+`workflow` scopes) can run git/merge/tests/tagging, but a full Gradle+NDK build is CI-only (`build.yml`), and it has the AI to resolve conflicts. (b) A GitHub Action can detect upstream + do clean merges + build, but conflict resolution needs an LLM/secret or a human; no Anthropic/Codex secret is in the repo (`gh secret list` shows only the two keystore secrets). `update_buddy` (Java) can at most trigger/poll a workflow or report; it has no GitHub token (unverified: whether the app stores one; `Updates.get` is unauthenticated, `Updates.java:~159`).
- **GITHUB_TOKEN limits:** commits/tags pushed by a workflow with `GITHUB_TOKEN` do NOT trigger other workflows (documented GitHub behavior, unverified here against the docs page); the repo default workflow permission is read (`gh api .../actions/permissions/workflow` → `default_workflow_permissions: read`, though build.yml sets `contents: write`). So an Action that pushes a tag needs a PAT or must build in the same run. Pushing changes under `.github/workflows` needs `workflow` scope (the local gh token has it).
- **Unattended tag push publishes an APK Nicholas hasn't reviewed.** `upstream-sync.md` step 4 requires confirm before PR/merge and a Codex cross-family review; the brief's done-when wants "green before publishing", and failures "stop with a clear message, nothing published". Plan must say which confirmations stay (golden rule 4 is in the playbook; not re-read here).
- **Semantic conflicts hidden from git:** clean textual merges can break behavior or compile (e.g. 2.3.10 changed `Guard.java`, `Tools.java`, `ChatHub.java` which fork features 004/007 also touch). Only compile + unit tests catch them; fork features have no UI/instrumented tests, so "keeps all fork features 001-007" is only partially testable (`app/src/test` JVM only).
- **Every merge conflicts on BuildInfo.java** (both sides bump); `docs/GUIDE.md` and `strings.xml` (22 locales) are frequent hot spots (upstream touched all 20+ `values-*/strings.xml`).
- **Signing:** installed fork APK must be signed with the fork key; CI does it from secrets. A locally built APK would not update in place (Android signature check; also `Updates.install` demands newer code).
- **Upstream release vs main:** upstream/main may be ahead of the latest upstream *release* (unreleased commits). The brief says merge when upstream has a newer *release*; the merge point should then be the release tag (`v2.3.10`), not `upstream/main` (playbook step 1 says `upstream/main`; mismatch to resolve). Currently `upstream/main` = f93a593, whose version is 2.3.10 (`git diff` of BuildInfo), so both coincide today (unverified that tag v2.3.10 points to f93a593: `git ls-remote --tags upstream` listed only up to v2.3.9 after my `git fetch upstream` output got truncated; `gh release list` does show v2.3.10).
- Rate limits: unauthenticated GitHub API 60/h from the phone (`Updates.get`), fine for one extra call per check (unverified).
- Branch protection / CI-on-PR: build.yml runs on `pull_request`, so a sync PR gets CI (`build.yml:3-7`). Open `feat/*` branches should be refreshed after (playbook step 5): currently `feat/008-upstream-in-update` is the only one known (git status).
