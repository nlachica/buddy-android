# Research: 036-hey-buddy-locked
Researched 2026-11-22 (claude-sonnet-5-5). Code facts are from branch `feat/036-hey-buddy-locked` at 48e9829.

## Summary
- **Code reading finds no lock check anywhere on the wake path.** `grep -n "Keyguard|isKeyguard|screenOn|PowerManager|isInteractive|locked"` over `WakeService.java`, `WakeMic.java`, `WakeWord.java` and `WakeLoop`'s callers returns nothing. Lock checks exist only in `BuddyService.java:131,161,209`, `Triggers.java:1143` (notification rules only, `Triggers.java:661`) and `WakeActivity.java`. Nothing in the code deliberately stops detection or drops a turn while locked.
- **No device evidence yet, so the cause is still unknown.** This chat has no `logcat` (`logcat: command not found`) and `adb devices` lists no device. The detector logs only through `android.util.Log` (tags `HeyBuddy` at `WakeService.java:238`, `BuddyWake` at `WakeWord.java:162`, `WakeMic.java:47,60,70`), with no file log. The first job for the Planner is a locked-screen diagnosis run (recipe below) that reads those tags.
- **Three candidate causes, each ruled in or out by a different log line** (see "Hypotheses"): (A) the detector's microphone is silenced or killed while the screen is off or locked; (B) it detects, but the turn can't start or finish while locked (recognizer, dictation, waves, bubble); (C) it works, but the spoken reply or the agent run is blocked. Each has code that could matter, listed below.
- **The service is a standard microphone foreground service** (`app/src/watchlink/AndroidManifest.xml:10-13`, `foregroundServiceType="microphone"`; `startForeground(..., FOREGROUND_SERVICE_TYPE_MICROPHONE)` at `WakeService.java:104`). It holds no wake lock of its own; the plan relied on the open recording keeping the CPU awake (`032 plan.md:153`; `032 research.md:72` marks this "unverified"). **Screen-off was never tested on the phone**: `032 verify.md:26-27` lists "screen off and unplugged 5 min, then 5 'hey buddy' (≥ 4)" as a pending post-release check.
- **The `WAKE_LOCK` permission is already held** (`AndroidManifest.xml:20`) and `Triggers.java:1147-1152` shows the house pattern for a `PARTIAL_WAKE_LOCK`. A wake lock costs battery, so it would need to stay inside `032 battery.md`'s budget ("a few percent an hour with the screen off", an estimate).
- **A turn on a locked phone is built to run hidden.** `Bubble.applyEnabled` keeps a "hey buddy" turn's listening when the keyguard comes up (`Bubble.java:1134`, sync commit 869e30d), and `showWaves` skips the waves when the bubble is hidden (`Bubble.java:1799`). So 032's "answer while locked" decision (`032 decisions.md`, "Q3 = (a) answer while locked") exists in code, but was **never verified on a locked phone**.
- **Where the phone itself could be the cause** (all unverified, no source read): Samsung One UI "Sleeping apps / Deep sleeping apps" and per-app battery "Restricted", Android's microphone privacy/lock behaviour for the system speech recognizer, and `Settings → Apps → Buddy → Battery → Unrestricted` (the app holds `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, per `032 research.md:81`). The brief says to stop at "a phone setting" if that is the whole answer.
- **Test constraint:** no JVM runs on this phone (`032 decisions.md`, "No JVM works on this phone"), so unit tests are CI-only. The wake path (`WakeService`, `WakeMic`, `Bubble.talk`, `WakeWord.onWake/openWindow`) has no unit test; it is covered only by device checks.

## Hypotheses (what each predicts in the logs on a locked phone)
Reproduce with: Hey Buddy on, phone locked and screen off for 1+ minute (not plugged in, then also plugged in), say "hey buddy, what time is it" 5 times at arm's length. Read `logcat -s HeyBuddy BuddyWake` over a wireless adb session from another machine (`adb tcpdump`/`adb logcat` needs Developer options; unverified that wireless debugging is on) or the bug-report route.
- **A. The detector doesn't hear.** No `HeyBuddy` score lines at all for the locked period (or `BuddyWake: mic … did not start recording`, `read error`, or `service started` missing / `paused`). Causes: Samsung sleeping/deep-sleeping apps or battery "Restricted" stops or freezes the service (`032 research.md:81`, unverified); the CPU suspends between mic buffers (no wake lock, `032 plan.md:153`); another app's recording makes Buddy pause (A2); on Android 14+ the system silences background capture for an app with no visible UI (unverified, not found in docs read). Fixes would be a phone setting (Unrestricted battery; remove from sleeping apps), a `PARTIAL_WAKE_LOCK` held while idle-listening (cost: battery, bounded by `032 battery.md`), or a restart-on-silence watchdog.
- **B. Detected, no turn, or a turn that dies.** `HeyBuddy` shows a wake line, `BuddyWake: turn N` may or may not follow. If no `turn N`: `WakeWord.onWake` dropped it (state not IDLE, `svc.bubble() == null`). If `turn N` appears but nothing is heard: `Voice.listen` failed under the lock (Claude/ChatGPT dictation WebView on a locked screen; the system recognizer refusing a locked, screen-off client — unverified; `Bubble.talk` returns early if `Voice.micAllowed` is false). `listen` errors surface only as toasts (`WakeWord.nothing/ended`), which the user won't see locked, so add log lines for them.
- **C. Heard and sent, nothing spoken.** The chat shows the request in the app after unlock, but no audio. Candidates: `Voice.speak` TTS while locked/screen-off with audio route or `AudioRoute.use` focus (`Voice.listen:188`); the agent run being held while locked (the `keepAwake.update()` calls in `BuddyService.java:152,194`; `KeepAwake` class exists at `BuddyService.java:59`; its screen-off behaviour not read). Tell from the chat transcript after unlock and `logcat -s BuddyWake`.

## Constraints and risks
- **Battery:** any wake lock or screen-on trick must stay inside `032 battery.md` (estimate: a few percent an hour, screen off; trigger for an energy gate is more than 10 ms per hop). A wake lock held during idle listening could raise it; measure with `dumpsys batterystats` as `battery.md` describes.
- **Privacy:** answering while locked was an accepted decision (`032 plan.md:474`, Q3 = a); approval cards still need unlock. Waking the screen (`WakeActivity` style) would be a new behaviour, not currently accepted.
- **No device log or JVM available to the pipeline**, so evidence needs Nicholas's phone: the Verifier's "works with the screen locked and off, verified on the phone" cannot run in CI. The fix may have to ship with a diagnostic log first.
- **Silent failure points** with no log: `Voice.listen` errors reach only a toast (`WakeWord.java:192-199`), and `WakeWord.onWake`'s early `drop()` at `:149-152` logs nothing.
- **Flavor:** github fork only; keep everything out of the F-Droid/reproducible build path as 032 did.
