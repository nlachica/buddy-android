## 2026-11-15 Research (Researcher, claude-sonnet-5-5)
Paths are under `app/src/main/java/app/buddy/assistant/` unless noted. Read-only pass; nothing built or run on a device.

## Summary
- **Nothing exposes Buddy's own settings to an agent today.** Prefs (`Prefs.java`, SharedPreferences "buddy", ~170 accessors, `Prefs.java:11`) is read/written only by Activities and services; no MCP tool touches it. Secrets (agent API keys, MCP server keys) are a separate Keystore-encrypted store (`Secrets.java:14-40`), never in Prefs. But Prefs itself holds two bearer tokens (`token` = MCP server, `Prefs.java:19`; `bg_token` = background helper) that a settings tool must mask.
- **"User-only" is enforced at the touch layer, not the data layer.** `Guard.offLimits` (`Guard.java:485`) refuses any tap/type on Buddy's own UI, or, with `Prefs.agentsTapBuddy` on, on views marked `Ui.protect(...)` (`Ui.java:377-392`, accessibility extra `app.buddy.protected`) and on the accessibility overlay (bubble, card). Tools.java calls it from `guard()` (`Tools.java:1603`), `typeText` (`:1746`), `guardStroke` (`:1897-1903`), answering `ownScreen()` (`:1698`). A direct tool bypasses all of it, so the fork's tool must carry its own gate.
- **Protected (user-only) screens** (`protect(`): App permissions (`AppPermissionsActivity.java:72`), API keys (`ApiKeysActivity.java:54,298,433`), Background (`BackgroundActivity.java:50`), Backup (`BackupActivity.java:47`), in `ChatActivity`: approval card (`:211`), Linux tools chip (`:98`), bg chip (`:102`), Chat options button (`:129`) and its sheets (`:1076,1213,1246,1353,1576`). GUIDE.md also lists MCP servers, Notification rules, Scheduled, Skills as user-only (`docs/GUIDE.md:202`). Check `McpServersActivity`/`RulesActivity`/`SchedulesActivity`/`SkillsActivity` protect status in the plan (unverified: they did not show in the `protect(` grep, so GUIDE.md and the code may disagree).
- **The approval path a new tool should reuse is `svc.askConfirm(summary, false)`** (`BuddyService.java:877`): blocks the tool thread on a bubble card (`card()` `:941`) and returns `APPROVED…`/`DENIED…`/`CHANGES REQUESTED…`. `canAuto=false` skips rule countdown/"Don't ask" auto-approval (`:882-897`). Existing in-tool precedents: `open_url` in rule runs (`Tools.java:~545`), `phone_shell` (`:639-642`). Helpers get `DENIED` (`:880`); rule runs get `NOT_NOW` when locked (`:898`).
- **Do not use the `confirm` tool's path as the gate.** `confirm` can return `APPROVED automatically` for trusted apps (`Tools.java:479-484`) and a prior confirm's text can satisfy `Guard.takeApproval` for 10 min (`Guard.java:90,340-360`). The new tool should call `askConfirm` directly, per change, and not consult `Guard.autonomous`/`takeApproval`.
- **Agents can't answer cards by touch:** card/bubble are accessibility-overlay windows that taps never land on (`Guard.java:462-470,485-497`, comment `:11-17`); `guard()` also blocks all taps while `bubble.confirming()` (`Tools.java:1600-1602`, `:1897`). Remaining side-channel: `phone_shell` could `input tap`; it is only a regex tripwire `SHELL_NO` (`Tools.java:614-616`, comment `:609-613` "a tripwire, not a wall") plus its own ask card and a user-only switch. The "approval cards can't be answered by the agent (tested)" criterion needs a test that covers this.
- **Self-update today (GitHub flavor):** `update_buddy` (`Tools.java:299-306`) → `Updates.latest()` hits the GitHub API of the hard-coded **upstream** repo `ghorbelhamdi/buddy-android` (`Updates.java:41,50`) and only accepts asset `buddy.apk` under that repo's URL (`Updates.java:73-76`). On the fork this would offer *official* releases, signed with upstream's key, to a fork install: Android would refuse them (different signature), and the daily check (`Updates.maybeCheck`, `BuddyService.java:72`) would notify about upstream versions. Needs a decision.
- **`install_apk`** (`Tools.java:292-296`, `installApk` `:2102-2132`) already installs an arbitrary APK from Buddy's Linux (`/root/...` path, canonicalized inside `Linux.root`) or `http://127.0.0.1:port`. Needs Linux tools in the chat (`devFor`, `ChatHub.java:510`) and Android's "install unknown apps" for Buddy. It copies to `cacheDir/install.apk` and opens the system installer via `FilesProvider` (`FilesProvider.java:33-47`). **The user taps Install; no Buddy card is involved**: the system installer is the confirm. `wait_for_install` polls `getPackageInfo` (`Tools.java:2064-2085`).
- **Version rule:** the in-app downloader refuses an APK that isn't the same package with a higher `versionCode` (`Updates.java:96-100`); `install_apk` has no such check (Android itself rejects downgrades/wrong signature). `versionCode` and `VERSION` are read from `BuildInfo.java:5-6` by Gradle (`app/build.gradle.kts:7-8`), so a self-built update must bump `VERSION_CODE` (now 205, "2.3.7").
- **Fork CI can produce a signed APK:** `.github/workflows/build.yml` signs with repo secrets `BUDDY_KEYSTORE_BASE64`/`BUDDY_KEYSTORE_PASSWORD` when present (`:36-48`, `app/build.gradle.kts:30-61`); both secrets exist on `nlachica/buddy-android` (set 2026-11-15T07:25Z, `gh secret list`). Latest feature-branch run 43701551913 succeeded and uploaded artifact `buddy-apk` (6.3 MB, not expired) (`gh api …/artifacts`). Whether that APK was signed with the key: unverified (not downloaded). No GitHub release exists yet on the fork (`gh release list` empty). The workflow only publishes a release on `v*` tags; branch/PR runs only upload an artifact (which needs a GitHub login to download: `gh run download`).

## Prior art
- Upstream documents the reason for user-only in `Guard.java:11-17` ("The agent can't tap Buddy's own bubble or approval card, so it can't approve for the user"; Guard is "the hard limit… enforced here, in Buddy"), `Ui.java:379-382` ("Agents may never tap or type in this view, even when 'Let agents tap Buddy's screens' is on"), per-screen comments (API keys "agents never see or change keys", App permissions "agents never change", Backup "only the user backs up or restores", Linux chip "agents never switch it", approval card "only the user answers it", Chat options "only the user sets what runs on its own"), `Prefs.java:141-144`, and `docs/GUIDE.md:202` ("so it can't approve for you or loosen the rules"). Theme: agents must not loosen their own limits, see/change keys, or approve. A direct settings tool deliberately goes against the "loosen the rules" part, which is why the brief puts every change behind a card.
- Upstream issue #33 (ghorbelhamdi/buddy-android, "Agents still blocked… with 'Allow agents to tap Buddy's screens' on"): agents refuse on their own because Buddy's system prompt says never tap Buddy's screens; the fix told agents which parts are open (`Tools.ownScreen :1698-1705`). Lesson: BLOCKED texts and the system prompt must match the new capability, or the agent will treat the tool as a rule violation. The agent's system prompt is `linux/system-prompt.md` (confirm rules at `:24`; it also carries the "never tap Buddy's own bubble, cards or screens" line per the issue) and needs updating for a settings tool (line not re-checked).
- `phone_shell` (upstream issue #22) is the closest precedent for an agent-run "outside the tap layer" action: gated by user-only switches (Settings → Background mode → Phone commands), Linux tools per chat, a tripwire regex, and a per-command card (`Tools.java:614-652`). It explicitly blocks `app.buddy.assistant` and the accessibility-service settings (`SHELL_NO`), i.e. upstream's stance is that Buddy's own settings are the user's (`:636`).
- `Backup.java:170` kills the process after restore (precedent for restart-style actions).

## Constraints and risks
- **Self-install and the running chat:** installing an update replaces the package, which kills Buddy's process and its agent (`ChatHub.java:70-72` comment "Android closed Buddy (an update…), and its agent with it"). On the next start, chats marked busy are cleared and get a "interrupted" note (`ChatHub.java:74-80`); chats/sessions persist on disk (`Sessions.save`) and Prefs persist across an update, so "chats and settings intact" is the existing behavior. The agent cannot report success afterwards in the same turn (`updateBuddy` text already says "Buddy restarts once it's installed, which ends this task", `Tools.java:2158`). Scheduled alarms are re-armed on `MY_PACKAGE_REPLACED` (`AndroidManifest.xml:228-236`). After the update there is nothing that resumes the agent's task (unverified: no `MY_PACKAGE_REPLACED` handler outside `Schedules.Boot`; grep found only that one).
- **Signing:** an update only installs over the same signing key; the fork's CI key (secrets above) is the only key that updates a fork install. The phone still runs the *official* Buddy (brief); a fork APK will not install over it until it is uninstalled (data loss) or the fork build gets a different applicationId — the brief says the switch is handled in 003's verify (no `docs/features/003-wear-companion/verify.md` exists yet, so unconfirmed). `applicationId app.buddy.assistant` for both (`app/build.gradle.kts:21`).
- **The in-app updater points at upstream** (see Summary). Using it from the fork either offers upstream's APK (fails signature) or needs `REPO`/`API` repointed to `nlachica/buddy-android` (`Updates.java:41,50`) plus a released `buddy.apk` asset; a branch build is only a workflow *artifact* (needs GitHub auth to download), not a release asset.
- **Download path for a CI build:** options (not designed): `gh run download` in Buddy's Linux (gh is installable via `GitHub.java`) then `install_apk /path.apk`; or tag → release asset. `install_apk` needs the agent to have Linux tools and "install unknown apps" for Buddy.
- **No Buddy card exists for installs**; Android's installer is the user's confirm. Brief wants "one approval card first": that is an addition (`askConfirm` before calling the existing open-installer code), plus the system installer tap after it (two taps unless `canRequestPackageInstalls` + user-initiated flow allows silent install — silent self-update needs `PackageInstaller` and `UPDATE_PACKAGES_WITHOUT_USER_ACTION` (Android 12+, only when Buddy is the installer-of-record); unverified for this device).
- **Untrusted content:** the agent's chat may carry prompt-injected text; a settings tool that can loosen trust levels, allow lists, `phoneShell`, `agentsTapBuddy`, MCP servers (which add tools/URLs the relay forwards, `McpServers.relay :305`) is a privilege-escalation path, so the card must show setting, old and new value verbatim, and the tool must refuse in rule runs and for helpers (precedents above). `confirm`'s "CHANGES REQUESTED" answers need handling too.
- **Secrets:** `Prefs.token`, `bg_token`, API keys (`Secrets`), MCP server headers/keys (`McpServers.secretName :77`), `signedAgents`, any `*_token` must be masked/omitted in listing (`Prefs.agentToken` is a boolean, not a secret).
- **F-Droid flavor:** `Flavor.FDROID` gates updater UI/tool (`Tools.java:298`, `BuddyService.java:72`); a self-modify tool with install should be `!Flavor.FDROID` only, like the updater; the settings tool is flavor-neutral but "keeps F-Droid unaffected" needs the same gating decision. F-Droid reproducibility check on `main` (CI step "Check the F-Droid APK is reproducible") failed on the last two main runs (runs 43686152920, 43686145143) after publishing, so check whether that is pre-existing (unverified cause).
- **Docs/strings:** many UI strings are localized (Guard patterns span ~20 languages); card text for a new tool uses `R.string.tools_card_*` (e.g. `tools_card_shell`, `tools_card_open_url`). How many `values-*` locales exist and whether lint requires all: unverified.
