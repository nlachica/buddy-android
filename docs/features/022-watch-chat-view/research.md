## Summary
- The watch has no history today. `TalkActivity.draw()` shows only `Talk.lines` (this process's live conversation) and only when `chat.equals(Talk.chat)` (`wear/.../TalkActivity.java:239-251`). Opening another chat from the list shows the face, mic and call buttons only. `Talk.lines` is cleared whenever `begin()` starts a different chat (`Talk.java:162-171`).
- Phone side: no message-history path exists. Paths are CHATS, SEND, STATUS in `WatchLink.onMessageReceived` (`app/src/watchlink/.../WatchLink.java:30,73-86`). A new path pair (e.g. `/buddy/history` W→P request, P→W answer) fits the table in `docs/features/003-wear-companion/plan.md:109-115`. Wear's `Phone.java:279-284` holds the path constants (add there too).
- The data is ready: `Sessions.Session.messages` is `List<Msg>{kind, text, files}` (`Sessions.java:28-43,117`). Kinds are `USER, BUDDY, STEP, ERROR, NOTE` (`Bubble.java:2702`). Buddy keeps up to 2000 per chat (`Sessions.MAX_MESSAGES`, `Sessions.java:24`; phone screen shows the latest `PAGE = 150`, `:26`). The watch needs a much smaller cap.
- Size limit: MessageClient carries 100 KB; the existing chat list guards at `LIST_MAX_BYTES = 90_000` (`WatchLink.java:33,103`). A history reply needs the same byte guard plus a per-message length cap (reply text is already capped at `SPOKEN_MAX = 3000` for the relay, `WatchLink.java:34,163`). Both caps are reusable ideas.
- Text cleaning: `Voice.spoken(app, text)` strips markdown/code/URLs (`Voice.java:223-232`) and is what `/buddy/reply` already sends; reuse it so history reads like live replies. Messages with only attachments have empty `text`; `Msg.label()` gives a "📎 name" string (`Sessions.java:52-57`). STEP and NOTE messages are not conversation; skip or keep out of the first version (a decision for the Planner).
- Live updates: the phone relays only for **tracked** chats, i.e. runs the watch itself started (`tracked` map, `relay.onMessage` returns if `node == null`, `WatchLink.java:42,156-158`). A reply in a chat that the phone user started (or any scheduled/rule run) is not sent to the watch today. "A new reply appears while open" for phone-started runs needs a new subscription (watch says "I'm viewing chat X", phone's `ChatHub.Listener` (`ChatHub.java:16-20,169-175`) pushes BUDDY/ERROR/USER messages for it), or periodic re-fetch. For watch-started runs `Talk` already receives `/buddy/heard|reply|done` while `waiting`, and also appends to `Talk.lines`.
- Duplication risk: for a watch-started run, the history snapshot (fetched on open) and `Talk.lines` (live) overlap: the phone already holds the USER message and replies in `messages`. The Planner must pick one source of truth for the open chat (e.g. render history, then only lines added after the fetch, or re-fetch on `done`). `Talk.lines` has no ids/timestamps (`Talk.java:51-59`).
- UI: `TalkActivity` is plain views, no Wear/AndroidX libs (`wear/build.gradle.kts:62` only has play-services-wearable). Layout: pill title, `ScrollView` weight 1, then mic + call row (`TalkActivity.java:76-133`). The scroll area is already inside the layout above the buttons, so the buttons stay reachable. The bezel works through `scroll.setFocusableInTouchMode(true)` ("the Watch4's bezel scrolls what has focus", `TalkActivity.java:95`, `ChatsActivity.java:53,122`). Note `ChatsActivity` calls `scroll.requestFocus()` in `header()`; `TalkActivity` never calls `requestFocus()` (grep: none), so bezel scrolling in the talk screen is unverified (unverified on device).
- Auto-scroll: `draw()` ends with `scroll.post(() -> scroll.fullScroll(View.FOCUS_DOWN))` on every redraw (`TalkActivity.java:262`). This yanks the user back to the bottom on any update, which conflicts with "scroll up while a reply arrives"; with history it matters (also `fullScroll(FOCUS_DOWN)` moves focus). Phone had the same class of bug: features 012/017 chat-scroll(-jump).
- Draw cost: `draw()` does `removeAllViews()` and rebuilds all TextViews each call (`TalkActivity.java:238`); fine for ~tens of lines, wasteful for hundreds. Another reason for a small cap (e.g. last N messages and a text length cap).

## Constraints and risks
- Message size: 100 KB per MessageClient message (`WatchLink.java:32`); budget by bytes, not only count. A multi-byte-safe truncation is needed (the `chats()` code truncates by `String.length`, `:100`).
- Phone must be reachable and Buddy's accessibility service on is **not** needed for reading history (only `deliver` checks `BuddyService.get()`, `WatchLink.java:118`); history should work without it. Unknown/deleted chat id (e.g. New chat the phone hasn't heard, `Talk.fresh` / `TalkActivity.fresh`): history must return empty without error; do not fetch for a fresh New chat (`TalkActivity.java:57-58,73`).
- Watch-started runs: `Talk.lines` and fetched history overlap (see Summary); also `Talk.lines` is cleared on starting a talk for a different chat, so history is the only way to show other chats.
- Live updates for phone-started runs need new phone state (a "watched chat" per node + a listener registered in ChatHub, wake/cleanup rules, removed when the watch leaves). `tracked` + `ses.watch = true` have side effects (silence phone read-aloud, no run-ended notification: `Sessions.java` `watch` field, `ChatHub.java:1150-1153`) so viewing must **not** reuse `tracked`/`watch`; a separate map is needed (design point).
- Redraw rebuilds the view tree and force-scrolls to the end (`TalkActivity.java:238,262`): must not fight the user's manual scroll once history exists.
- Round screen: use `Look.sidePad` and the top margin for the pill (`TalkActivity.java:90-92`); long messages at 15sp with 26dp side padding already used for replies.
- Privacy/safety: messages go over the paired Data Layer only (same as chat titles today). Chat text may include sensitive content; nothing new in exposure class beyond replies already sent. No logging of content in new code (convention not verified).
- Process death: `Talk.lines` is process-wide static; history fetched on each open avoids stale state (no persistence needed).
- Both modules' Java compile in CI only on `:wear:assembleRelease`; no instrumentation tests exist.
